# アーキテクチャ設計

要求資料に、アーキテクチャの条件はほとんどない。書けない所は、ないことか、未決事項を書いた。

## 概要・設計条件

- 対象範囲：注文の受付から、出荷の完了まで（`../product/goals.md` の範囲）。請求、入金、返品、会計システムへの連携は範囲外である。
- 品質目標：QS-01（同時の注文でも限度額を超えて承認しない）、QS-02（判定の理由を残す）、QS-03（問題のない注文をその日のうちに出荷の準備へ）。
- 前提と制約：技術、予算、期間、運用の制約は、要求資料にない。

## 基本方針

- 設計原則と技術の選定：要求資料にない。決まっていない。
- 重要な判断：有効な ADR は、まだない。

## システムコンテキスト

| 外部 | やり取り | 出所 |
| --- | --- | --- |
| お客様の購買担当者 | 注文書を FAX、メール、Web の画面で送る。Web の画面の受付が範囲かは Q-25 | 要求資料 §3 |
| 受注担当者 | 注文を入力し、提出する。結果をお客様に連絡する | 要求資料 §3 |
| 与信担当者 | 審査に回った注文を、承認するか断るか決める | 要求資料 §3 |
| 倉庫担当者 | 出荷の指示を受け、出荷の開始と完了を記録する | 要求資料 §3 |
| 会計システム | 連携は別の計画で扱う。範囲外 | 要求資料 §2 |
| 未決済残高、与信の限度額、取引停止中の区分、高リスクの商品の区分、在庫の数を持つもの | 持ち主と入手の方法が決まっていない（Q-16、Q-17、Q-31、Q-18、Q-32） | 要求資料 §5、§4 |

## 実行時・配置

要求資料に、実行環境、配置、冗長化の記述はない。トランザクションの範囲と、同期か非同期かの選択は、Q-27、Q-36、Q-24 で決める。業務上の事実の流れは `../domain/facts.md` を引く。

## 横断的な方式

- セキュリティ、監視と運用、可用性と性能：要求資料にない。
- データ：与信の判定の理由を残す（QS-02）。残す期間は Q-04。
- エラー処理：業務上の拒否（JDG-CREDIT-01 の「断る」、状態遷移表の「×」）と、技術的な失敗を分ける。技術的な失敗の扱いは決まっていない（Q-24）。
