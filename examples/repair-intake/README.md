# 例題：家電の修理受付

画面、帳票、既存のテーブル、AI のツールが作った試作を手がかりにして、業務の対象の形を書く例題である。

## 何を示すか

- 同じ修理依頼書で「見積だけ」と「修理を依頼」の両方を受け付ける。この二つを一つの形にまとめず、別の業務の対象として書く（[processes.md](../../docs/processes.md) §1.6 手順 2）。
- 画面の案の列、いまのテーブルの列、試作のスキーマを、そのまま業務の対象の形にしない。項目ごとに、値がどこから来るかを確かめ、業務の対象の形の表、事実、業務ルール、画面だけの項目に振り分ける（同 手順 3）。
- 見積の金額や修理が終わった日時のように、状態によってある情報とない情報を、状態ごとに列を立てた表で書く（[notation.md](../../docs/notation.md) §2.6）。
- お客様の住所が変わったとき、返送先の住所も変わるのか、依頼書に書かれた時点のまま残るのかを、推測で決めず、未決事項にする。
- 値を入れた見本には、資料にある値だけを使う。記入済みの依頼書が資料にないので、値を入れた見本は未決事項にした。

## 入力

`input/materials.md`：例題のために作った架空の資料である。次の五つから成る。

- 要求資料（抜粋）
- 修理依頼書の様式（空の様式）
- 画面の案（受付担当者の「修理依頼の一覧」）
- いまのシステムのテーブル（既存のコード）
- AI のプロトタイピングツールが作った試作とスキーマ

## どの手順で書いたか

整理された要求から入る手順（[processes.md](../../docs/processes.md) §2）の 1〜7 と 10 に、画面、帳票、試作を手がかりにする手順（同 §1.6）と、既存のコードの現状を読む手順の 1〜3（同 §3）を合わせた。着手する機能は「修理依頼の受付」である。

- 手順 1：要求資料と、記入していない様式の写しを `docs/product/upstream/` に置いた。いまのシステムのテーブルは、コードなので写しを置かない。
- 手順 2：空白と食い違いを、`docs/questions.md` に未決事項として置いた。
- 手順 3：`docs/domain/glossary.md`。
- 手順 4：`docs/domain/facts.md`、`docs/domain/things.md`。画面、様式、テーブルの項目は、§1.6 の手順 3 の表に沿って、表の右の列の文書に書いた。画面の項目ごとの一覧は、文書に残していない。
- 手順 5：`docs/domain/rules.md`。判定として書けるものは、資料になかった。
- 手順 6：`docs/domain/lifecycles.md`。
- 手順 7：`docs/domain/contexts.md`。コンテキストは一つで、ほかのコンテキストとの受け渡しの約束は、資料にない。
- 手順 10：画面の案の配置を `docs/spec/README.md` に置いた。既存のコードから、`docs/design/model/修理受付.md` と `docs/design/model/issues.md` を、現状（`as-is`）として書いた。

## AI のツールが作ったスキーマを採らなかったこと

試作のスキーマ（`repair_list_rows`）は、論理モデルにも設計課題にも書いていない。採るかを決める前の材料として読み、採らないと判断した（[processes.md](../../docs/processes.md) §1.6 手順 5）。理由の要旨は次のとおりである。

- 画面の案の列（受付番号、お客様名、製品、状況、前回の修理からの日数）を、そのまま一つの表にしたもので、画面の行が業務の対象の形になっている（AP-19）。
- 見積だけの依頼と修理の依頼、依頼とお客様と製品が、一つの行に混ざる。
- お客様名と製品を文字列で持ち、いまのテーブル `repair_requests` とのつながりがない。同じ情報が二か所に散らばる。
- 日数を整数で保存している。状況は自由な文字列で、すべての列が空を許す。

この例題では、画面の一覧の行は、依頼、お客様などの業務の対象から読み出す応答の形として扱う（`docs/spec/README.md`）。採ると決めたときは、論理モデルに仮説（`to-be`）で書く。

## 書いていない文書と、その理由

この例題が示すのは、画面、帳票、既存のテーブル、試作を手がかりにした、業務の対象の形の書き方である。次の文書は、その範囲の外なので書いていない。

| 文書 | 理由 |
| --- | --- |
| `docs/product/goals.md`、`docs/product/quality.md` | 目的と範囲の要約、品質シナリオは、業務の対象の形の書き方に関わらない。要求資料の抜粋に、品質の要求もない |
| `docs/architecture/` | アーキテクチャ設計の例ではない |
| `docs/decisions/` | 記録の線を超える判断が、まだ出ていない |
| `docs/spec/` のユースケース（`UC-`） | 画面の案の配置だけを置いた |
| `docs/design/model/shared.md` | 共有する値がない（コンテキストが一つ） |

## 読み合わせ

読み合わせはしていないので、決定の印の項目はない。業務の対象の形の表も、すべて仮説か要確認である。
