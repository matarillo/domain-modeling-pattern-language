# 手順

この文書は、三つの入口ごとに、文書をどの順で書き、どう保つかを示す。どの入口でも、[document-system.md](document-system.md) の同じ置き場に書く。入口の違いは、何から書き始めるかと、最初の印にだけ現れる。

- 各ステップの末尾の `MP-nn` は、そのステップで使うパターンである（[pattern-language.md](pattern-language.md)）。
- 手順は、工程を固定するものではない。機能を縦に薄く作るたびに、必要なステップだけを、使う直前に行う（MP-30）。

| 入口 | 正本 | 確かさ |
| --- | --- | --- |
| 整理された要求から入る（§2） | 顧客の要求資料 | 公開された題材で現れている |
| 既存のコードから入る（§3） | 既存のコードとテスト | 公開された題材で現れている |
| ワークショップから入る（§4） | ワークショップでの合意 | 仮説。既知の手法の原典に基づいて組み立てたもので、題材でまだ確かめていない |

## 1. どの入口でも行うこと

### 1.1 始める前

1. 骨組み（`templates/`）を写し、置き場と識別子の規則を決める。AI には、白紙からではなく、骨組みと記法を渡して書かせる（MP-31）。
2. `AGENTS.md` に、AI 向けの規律を書く（MP-10）。
3. 文書の量を、答える問いで絞る。この機能に要る文書だけを作る（MP-01）。

### 1.2 AI が書き、人が決める

- AI は、モデルの案（境界の分け方、事実と状態の名前、判定の候補）を、仮説の印を付けて書いてよい。
- AI は、業務の値、基準、選択を補わない。空白と矛盾は未決事項にする（MP-15）。
- 決定の印を付けるのは、人の判断が記録に残っているときだけである（MP-12）。

### 1.3 未決事項が決まったら

[document-system.md](document-system.md) §8 の順に進める（MP-12、MP-07、MP-06）。AI は、判断記録を求めるかを決定者に尋ねてよいが、自分で決めない。

### 1.4 AI が生成し、人がレビューするもの

上流と文書の対応の確認や、上流の矛盾の検出を AI に行わせたときは、結果をレビューの場（PR の本文、課題の記録など）に置く。人が採った指摘だけを、未決事項か設計課題に移す（[document-system.md](document-system.md) §14）。

### 1.5 保つ

- 文書は完成させない。例、コード、テストで新しい事実が分かったら、確認前の状態に戻してでも直す。
- 見直すのは、着手する機能が触る範囲だけにする。全文の一括の見直しはしない（MP-30）。
- 言葉のずれが見つかったら、用語集を先に直す（MP-24）。

### 1.6 画面、帳票、試作を手がかりにする

要求資料やワークショップには、画面の案、帳票、動く試作が付いてくることが多い。AI が試作を作ることもある。これらは業務を知る手がかりになる。ただし、その形をそのまま業務の対象の形にすると、違う業務が一つにまとまったり、同じ情報があちこちに散らばったりする（AP-19）。着手する機能が触るものについて、次のように読む。

> この手順は、既知の手法の原典に基づいて組み立てた仮説であり、題材でも、人との場でも、まだ確かめていない。

1. **置く**：業務で使っている帳票と、いまのシステムの画面は、上流の写しとして置いてよい（[document-system.md](document-system.md) §3）。要求資料に付いてきた画面の案と、試作の画面は、写し（画像）を `spec/` に置き、配置だけを持たせる（`spec/` がなければ、このときに足す）。試作のコードは置かない。ワークショップで描いた画面のスケッチは残さない（§4 手順 5）。どの入口でも、最初に、記入済みの実物（ふつうのものと、困ったものを数件。個人の情報などは伏せる）を見せてもらうよう頼む。欄外の書き込み、使われない欄、別の用途に使われている欄は、空の様式からは見えない手がかりで、業務の対象の、値を入れた見本（[notation.md](notation.md) §2.6）の出どころにもなる。
2. **一つの用紙を、二つの業務が使っていないかを見る**：たとえば、同じ注文書で、見積の依頼も注文もできることがある。二つを一つの形にまとめない [Wlaschin 2024 §2.2]。必ずある情報、許されない状態、業務の段階が違うかを、資料で確かめる [kawasima 2021]。資料が違いを述べていれば、別の対象として書き、それぞれを運ぶ事実を立てる。述べていなければ、着手する機能の対象だけを書き、もう一方の形は書かない。「二つは、必ずある情報や決まりが違いますか」を未決事項にする（決定者は顧客）。
3. **項目ごとに、値がどこから来て、何に使われるかを確かめる**：すべての情報には、どこから来て、どこへ行くかがある [Dymitruk 2019]。項目ごとに、値が業務のどこから来て、何に使われるかを問う [Lauesen 2002 §2.3]。

   | 項目の値は、どこから来るか | 確かめた結果を書く文書 |
   | --- | --- |
   | 業務の相手や現物から知らされる（誰が、何を見て） | それを知らせる業務上の事実。値が業務の対象の一部なら、`domain/things.md` の、その対象の形の表に行を書く（事実の表には、対象の名前だけを書く） |
   | 担当者が決める（誰の権限で） | 決める業務上の事実か、判定（`domain/rules.md`） |
   | 前に起きた事実から | その事実の名前 |
   | 外から受け取る（ほかのコンテキスト、外部のシステム） | 受け渡しの約束 |
   | ほかの値から計算する | 業務ルールの識別子 |
   | システムが付ける（記録した日時、番号） | 論理モデル。それで見分けるかは、顧客に確かめる |

   - 入力する項目は、何に使うか（どの業務ルール、判定、帳票、ほかのコンテキストが使うか）も問う。
   - 値がどこから来るか、何に使われるかが見つからない項目は、画面だけの項目として扱う（[document-system.md](document-system.md) §4.2 の `spec/`）。
   - 画面の項目の並びを、そのまま業務の対象の形にしない（[notation.md](notation.md) §2.6）。
   - 確かめた結果は、上の表の右の列の文書（業務の対象の形の表、事実、受け渡しの約束、業務ルール、画面だけの項目）に書く。画面の項目ごとに値がどこから来るかを並べた一覧は、文書に残さない。
4. **反応を分けて記録する**：試作を見た顧客の反応は、二つに分ける [Lauesen 2002 §8.2.11]。
   - 「この情報が要る」：`domain/` の項目に書き、出所に、試作を見せた回を書く。
   - 「この画面のとおりにしたい」：利用者が実際の仕事に使ってみて確かめた試作についてだけ、`spec/` に画面の決まりとして書く。それ以外は `spec/` に決まりとして書かず、要る情報は `domain/` に仮説で書く。
   - どちらも、問いに答えてもらった項目だけを決定にする。「よさそう」「動いた」は、決定にしない（AP-08）。
5. **AI が作った試作やデータの形を、決定にしない**：データの形は、採るかを決める前の材料として読み、§3 の手順 3 の歪みの点検表で確かめる。画面の行をそのまま表にしたような形は、業務の対象の形に写さない（AP-19）。採ると決めるまでは、論理モデルにも設計課題にも書かず、気づいた歪みはレビューの場に置く（§1.4）。採ったら、論理モデルに仮説（時点は `to-be`）で書く。

- AI にこの確かめをさせたときは、§1.4 のとおり、結果をレビューの場に置く。

## 2. 整理された要求から入る

顧客が作った要求資料があり、決定者がいるときの入口である。要求資料がなく、業務を探っている段階なら、§4 から入る。

1. **写しを置く**：要求資料の写しを `product/upstream/` に、書き換えずに置く。`product/goals.md` に、目的、範囲、関わる人の要約と、写しの箇所への参照を書く。
2. **空白と矛盾を拾う**：要求資料の空白と食い違いを、一つずつ未決事項にする。数値や基準を補わない（MP-15）。
3. **言葉を決める**：誤解が設計やテストに響く言葉と、単独で使わない言葉を、用語集に書く（MP-24）。
4. **業務上の事実を並べる**：要求資料の業務の流れから、過去形の事実を拾い、主な流れを事実の並びで書く（MP-18）。事実が運ぶ業務の対象のうち、着手する機能に要るものは、対象の種類、初めて記録される事実、同じ対象とみなす条件、業務の対象の形の表、値を入れた見本を `domain/things.md` に書く（MP-36、[notation.md](notation.md) §2.6）。要求資料に画面や帳票が付いていれば、§1.6 の手順で読む。
5. **業務ルールと判定を書く**：決まりを一つずつ宣言的な文にし、出所を書く。判定は、問い、入力（定義まで）、許される答えを先に書く。複雑なルールには、三つの例を置く（MP-21、MP-22、MP-27）。
6. **状態遷移表を書く**：状態と出来事のすべての組み合わせを並べ、空いたマスを `×`、`／`、`？` で埋める。届く事実と、取消などの前後の入れ替わりも行にする（MP-23）。
7. **境界と受け渡しの約束を書く**：業務ルールが一緒に変わる所で境界の案を立て、受け渡しごとに、失敗したときの扱いを書く（MP-19、MP-20）。
8. **品質シナリオを書く**：品質の要求ごとに、目標の決定者と、確かめる担当と時期を書く。数値が決まっていなければ、未決事項を引く（MP-25）。
9. **読み合わせる**：顧客と、未決事項、業務ルールと例、状態遷移表を読み合わせる。業務の対象の形の表と、記法の部分集合のブロックは、問いに答えてもらってから、決定にする（MP-12）。業務の対象は、値を入れた見本から読み合わせる（[notation.md](notation.md) §3.3）。
10. **機能ごとに、着手の直前に詳しくする**：着手する機能に関わる業務ルール、判定、状態遷移だけを詳しくし、論理モデル（コードがなければ記法の全体）と仕様を書く（MP-30、MP-28、MP-29）。
11. **実装した後**：記法の全体のブロックを、コードの型の名前と論理型の属性の表に置き換える。業務ルールの「検証」を更新する（MP-14）。

**写しの残りを振り分ける**

手順 3〜8 で項目にならなかった写しの箇所は、次のどれかに振り分ける（[document-system.md](document-system.md) §3）。

- 画面、帳票、外部 API の振る舞い：`spec/` に、着手の直前に書く（手順 10）。それまでは、写しの表（`product/upstream/README.md`）に、着手のときに書くと書く。
- データの形：業務上の形は `domain/things.md` に書く（§1.6）。キーなどの構造は、着手の直前に論理モデルに書く（手順 10）。
- 上流が指定した方式や構成：`architecture/README.md` の設計条件に書き、写しの箇所を引く。
- 上流が決め続ける事柄（上流が定めたコード値、データの型や桁など）：写しに残し、使う所から引く。写しの表に、残す理由を書く。
- 範囲に入らない箇所：`product/goals.md` の範囲外に書く。
- 決まりなのか、例として示しただけなのかが分からない箇所：未決事項にする。

最初に項目にするのは、手順 3〜8 の粒度までである。画面と論理モデルの細部は、着手の直前に書く。

**終えた目安**

- 写しのうち範囲に入る箇所のすべてに、行き先がある。行き先は、出所にその箇所を書いた項目、未決事項、`product/goals.md` の範囲外、写しの表に理由を書いて残した箇所の、どれかである。
- 業務ルールと判定のすべてに、出所と合意状態がある。
- 複雑なルールに、例がある。
- 未決事項のすべてに、決定者と決める時期がある。
- 推測で補った数値がない。
- 業務の対象の形の表の行と、判定の入力のすべてに、その値がどこから来るかが書いてある。分からないものには、未決事項がある。
- 状態遷移表に、空いたマスがない。

## 3. 既存のコードから入る

既存のコードとテストから、現状のモデルを導く入口である。

1. **論理モデルを導く**：集約、値、操作、不変条件を、コードから `design/model/` に書く。印は `source: code`、`timepoint: as-is`、仮説とする。記法の全体は使わず、論理型の語彙で書く（MP-29）。
2. **強制レベルと検証を付ける**：不変条件ごとに、モデルがどこまで守っているか（強制、表明、外部、不成立）と、テストで固定されているかを書く（MP-13、MP-14）。
3. **歪みを設計課題に隔離する**：現状の記述の中に改善の方向を書かず、設計課題の台帳に置く。強制レベルが「強制」でない不変条件は、すべて課題に対応させる（MP-17）。着手する機能が触る範囲で、次の表（歪みの点検表）の形がないかも見る [Wlaschin 2024 §2.2、§2.3]、[kawasima n.d.a]、[kawasima n.d.b]、[IPA 2019 §7]。データベースやクラスの作りの問題は、設計課題にする。業務の意味を確かめる問いは、未決事項にし、手順 5 で `domain/` に書くその項目を要確認にする。答えを待たずに、手順 5 へ進んでよい。

   | コードやデータの形 | その形を見たときに疑うこと | 顧客への問い（業務の言葉にしてから出す） |
   | --- | --- | --- |
   | ないことがある項目（空を許す列など） | 状態によって違う情報ではないか | これがないのは、どんなときですか |
   | 作るときは空で、後から相手が入る参照 | 別々に作れる二つの対象の、つながりではないか | 〜が決まる前に、〜はありますか |
   | 種別や区分の印 | 別の業務ではないか | 二つは、同じ決まりに従いますか |
   | 印の組み合わせで決まる条件 | 名前のない業務の意味ではないか | この組み合わせを、業務では何と呼びますか |
   | 共通の土台（基底のクラス、共用の表） | 業務にない抽象ではないか | 業務では、これを何と呼びますか |
   | 二つの意味に使われている参照 | つながりの意味が混ざっていないか | 〜と〜は、同じ意味のつながりですか |
   | 更新日時、上書きされる値、削除の印 | 隠れた業務上の事実ではないか | これが変わるのは、どんなときですか |
   | 一つの項目に複数の意味（コードの上 2 桁が部、など）、住所1・住所2 のように番号で並べた項目、9999 のような特別な意味の値 | 別々の情報が一つに詰められていないか | この値の各部分は、別々に決まりますか |
   | 画面ごとのテーブル、画面ごとに重なる項目 | 同じ情報が散らばっていないか | この情報は、ほかの画面にも出ますか |

   - 状態を印で表している所は、AP-14 にも当たる。
   - この表は、既知の手法の原典から集めたもので、題材ではまだ確かめていない。
4. **取り決めがないことを書く**：コードに規定がない事項を、ドメイン未定義と書く。決めるべきなら未決事項を立てる（MP-16）。
5. **顧客と共有する文書を導く**：論理モデルから、業務ルール、判定、状態遷移、業務上の事実を `domain/` に導き、仮説として顧客に確かめる（MP-03、MP-21）。コードの振る舞いのうち、業務ルールにするのは、業務の言葉で書け、決定者が値や選択を決め、破れると業務に損害が出るものだけである。当たらないもの（値の精度、入力の形式など）は、不変条件か論理型として論理モデルに置き、業務ルールにしない。業務の対象の形も、着手する機能が触るものだけを `domain/things.md` に導く。テーブルやクラスの列を、そのまま業務の対象の形の表の行にしない（AP-19）。手順 3 で問いを立てた列から導いた行は、要確認にして、その未決事項を引く。
6. **直すときは、先に挙動を固定する**：設計課題に沿ってコードを直す前に、特性テストで現状の挙動を固定する [Feathers 2016]。挙動を変えるときは、そのテストを意図して反転させる（MP-33）。
7. **直したら作り直す**：直したコードに合わせて文書を差分で直さず、現在のコードから作り直す（MP-34）。

- 古いシステムを作った人をドメインエキスパートにすると、そのシステムの仕組みが、業務の要求として持ち込まれやすい [Brandolini 2016]。§4 と組み合わせるときは、注意する。

## 4. ワークショップから入る

ドメインエキスパートと話しながら、業務を探る入口である。要求が固まっていない段階に向く。

> この入口は、既知の手法の原典に基づいて組み立てた仮説であり、題材ではまだ確かめていない。

1. **場を準備する**：目的と範囲、描く業務の時点（現状か、あるべき姿か）、業務そのものを描くかシステムの使い方を描くかを決める。決定者に参加してもらう。
2. **会話の表記で探る**：付箋や絵文字の図など、会話の表記を使う（例：出来事を時系列に並べる [Brandolini 2021]、業務を文で語る [Hofer and Schwentner 2026a]、ルールを例で確かめる [Wynne 2015]）。§6 の問いかけの型を使う。
3. **その場で語り直す**：描いたものを最初から読み上げ、ドメインエキスパートに確かめる [Hofer and Schwentner 2026a]。
4. **論点を止めずに残す**：答えの出ない点、意見の割れた点は、議論を止めて論点として残し、先へ進む [Wynne 2015]、[Avanscoperta 2025a]。
5. **終わったら転記する**：作成物を保存せず、合意したことを次の置き場に転記する（MP-32）。

   | 会話で得たもの | 転記先 |
   | --- | --- |
   | 言葉 | `domain/glossary.md` |
   | 出来事と流れ | `domain/facts.md` |
   | 業務で使う文書や帳票の情報 | §1.6 の手順 2、3 で振り分ける（業務の対象が何から成るかは `domain/things.md`、言葉は `domain/glossary.md`） |
   | 判断に使う情報 | システムの判定の入力なら `domain/rules.md`、人が見て判断する照会なら `spec/`。どちらも、値がどこから来るかを確かめる（§1.6） |
   | ルール、例、質問 | `domain/rules.md`、`questions.md` |
   | 状態 | `domain/lifecycles.md` |
   | 境界の候補 | `domain/contexts.md` |
   | 論点（付箋の論点、質問のカード） | `questions.md` |

   - 画面のスケッチは、ほかの会話の作成物と同じく残さない。合意した項目だけを、上の表の行に転記する。

6. **印を付ける**：決定者がその場で確かめた項目だけを決定にし、出所にワークショップの回を書く。要約の読み上げに同意を得たときは、要約がはっきり指した項目だけを決定にする。ほかは仮説にする（MP-12）。
7. **完全性を確かめる**：すべての流れが、それ以上の行動の要らない状態で終わっているか、すべての論点が未決事項になっているか、状態遷移表に空いたマスがないかを確かめる [Brandolini 2022]（MP-23）。着手する機能が触る情報について、値がどこから来るかが分かっているか（§1.6）も確かめる。

## 5. 組み合わせる

| 組み合わせ | 進め方 |
| --- | --- |
| 既存のコードから現状を導き、ワークショップであるべき姿を詰める | §3 で `as-is` の文書を書く。あるべき姿は、版管理のブランチで文書を書き換え、`timepoint: to-be` にする。顧客には、ブランチの差分でレビューしてもらう。合意した後の、コードを変える順序と `as-is` に戻す時点は、[document-system.md](document-system.md) §9 にある（MP-35）。古いシステムを作った人の扱いに注意する（§3） |
| 要求から立てた未決事項を、ワークショップで解く | §2 の未決事項のうち、業務の探りが要るものを、§4 の場の議題にする。決まったことは、§1.3 の順に反映する |
| ワークショップで描いた業務を、要求として整理する | §4 で転記した文書を、§2 の手順 5 以降で詳しくする。出所はワークショップの回のまま残す |
| 現状から、何段階かかけてあるべき姿に移す | §3 で `as-is` の文書を書く。あるべき姿の全体は、ワークショップなどで話してよいが、文書の正本にしない。次の段階だけを、MP-35 のとおりブランチで書き、取り込んでから次の段階を見直す。その先の段階は、未決事項と設計課題に置く（[document-system.md](document-system.md) §9） |

- 組み合わせても、置き場は同じである。入口ごとに文書を分けない（MP-03）。

## 6. 問いかけの型の目録

要求が固まっていない段階で、業務の決まりや抜けを引き出すための問いである。手法を問わず使ってよい。手法の原典などから集めた問いで、このパターンランゲージの題材では、人の話し手との場で確かめていない。

| 何を引き出すか | 問いの例 | 出典 |
| --- | --- | --- |
| 次に起きる出来事と、その情報がどこから来るか | 次に何が起こりますか。その情報はどこから得るのですか。前に誰かが入力する場面がありますか。その情報は、後で何に使いますか | [Hofer and Schwentner 2026a]、[Lauesen 2002 §2.3] |
| 判断の仕方 | 次に何をするかを、どうやって決めるのですか | [Hofer and Schwentner 2026a] |
| 境界の候補 | どの活動が、一緒に属しますか | [Hofer and Schwentner 2021] |
| 語られていない決まり | それは、いつもそうですか。すぐにですか | [Brandolini 2022] |
| 判断に使う情報と人 | 選ぶとき、何を見ていますか。では、誰が選ぶのですか | [Brandolini 2022] |
| 境界での振る舞い | 例えば、〜の場合はどうなりますか。結果が言えなければ、質問にする | [Wynne 2015] |
| 業務上の成果 | どんな成果を期待していますか。それが満たされたとき、どんな証拠が見えますか | [Smart 2019] |
| 利用者のニーズ | その人は、このシステムで何をしたいのですか（顧客やチームの望みと分けて聞く） | [Wardley 2018a] |
| 技術を前提にしない例 | コンピューターがなかったら、この仕事はどう行われますか | [Cucumber 2026d] |
| 同時に正しく保つ要求 | それは、誰の仕事ですか。その人は、二つが同時に正しいことを求めますか | [Vernon 2011b] |
| 方針の文の曖昧さ | その上限は、何あたりですか。期間の区切りはいつですか | [Ross 2024] |
| 待ちと異常 | その間、何を待っていますか。待っている間に、何が起こりえますか | [statecharts.dev n.d.c] |
| 量と頻度 | それは、1 日に何件くらい起きますか。同時に起きることはありますか | 品質シナリオ（MP-25） |
| 値の単位と定義 | その金額は、税込みですか。通貨は何ですか。いつの時点の値を使いますか | 判定の入力（MP-22） |
| できないこと | この状態で、この操作（この知らせ）が来たら、どうなりますか | 状態遷移表の空いたマス（MP-23） |
| 境界の間の失敗 | 返事が来ない、遅れる、二度来るときは、どうしますか | 受け渡しの約束（MP-20） |
| 業務の対象どうしのつながりの移り変わり | このつながりが成り立ったことや外れたことを、後で調べますか。外れて、また成り立つことはありますか | 関係の履歴（[data-modeling-pattern-language](https://github.com/matarillo/data-modeling-pattern-language)） |
| 業務の対象の形の読み合わせ（同じ対象とみなす条件と、その時点の値のまま残るかを含む） | [notation.md](notation.md) §3.3 の問いの表 | 合意状態（MP-12）、同じ対象とみなす条件 [kawasima n.d.a]、[Wlaschin 2024 §5.6、§5.7] |
