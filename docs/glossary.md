# 用語

このパターンランゲージで使う語の定義である。一つの概念に一つの名前を当て、似て非なる概念は §3 で区別する。

- DDD とモデリングのコミュニティで定着した訳語を使う（§1）。
- このパターンランゲージが独自に定める語は、§2 にある。

## 1. 定着した語

| 語 | 原語 | 定義・注記 |
| --- | --- | --- |
| ドメイン | domain | 開発するシステムが支える業務の領域 |
| ドメインエキスパート | domain expert | 業務の知識を持ち、ルールを決める側の人 |
| 顧客 | — | 発注者として業務を決め、文書をレビューする側。ドメインエキスパートを含む |
| サブドメイン | subdomain | 業務の問題領域の区分。中核（core）、支援（supporting）、汎用（generic）に分ける |
| 境界づけられたコンテキスト | bounded context | 一つのモデルとユビキタス言語が一貫して成り立つ範囲。実行の単位や配置の単位とは限らない |
| コンテキストマップ | context map | 境界づけられたコンテキストのあいだの関係と、受け渡しの約束を表すもの |
| ユビキタス言語 | ubiquitous language | 開発チームとドメインエキスパートが、同じ意味で使う言葉。その記録を用語集と呼ぶ |
| 集約 | aggregate | 一つの単位として整合性を保つオブジェクトのまとまり |
| 不変条件 | invariant | モデルが常に成り立たせる性質 |
| 値オブジェクト（値） | value object | 識別子を持たず、属性の値で等価性が決まるもの |
| ドメインイベント | domain event | ドメインで起きた、業務上意味のある出来事。過去形で名付ける。この文書群では「業務上の事実」と呼ぶ（§2） |
| ワークフロー | workflow | きっかけ、入力、結果として起きる事実、副作用で書く、業務の処理の並び |
| 全域性 | totality | すべての入力に対して結果を返す性質。失敗も結果の値で表し、例外に頼らない |
| 結果整合性 | eventual consistency | 一時的な不整合を許し、最終的に整合させる方式 |
| 判断記録（DR） | decision record | 判断・意思決定の記録 |
| ADR | architecture decision record | 判断記録のうち、アーキテクチャに関するもの |
| 決定表 | decision table | 条件の組み合わせと、その結果を表にしたもの |

## 2. このパターンランゲージが定める語

| 語 | 定義 |
| --- | --- |
| 層 | 文書が答える問いによる区分。要求（なぜ作るのか）、要件（何を引き受けるのか）、仕様（外部設計。外からどう見えるか）、内部設計（内部をどう作るか）の四つ。工程の段階ではない |
| 観点 | 層を横断する、文書の置き場の区分。ドメイン設計とアーキテクチャ設計の二つ |
| ドメイン設計 | 顧客と開発チームの共通理解。実装技術に依存しない。業務の言葉、境界と約束、業務上の事実、業務の対象の形、業務ルールと判定、業務の状態の移り変わりを表す |
| アーキテクチャ設計 | システムを何を条件に、どの方針と構成で作るか。方式設計とも呼ぶ |
| 論理モデル | 実装技術に依存しないが、顧客と共有しないモデルの記述。集約、不変条件と強制レベル、操作の型、設計課題。内部設計の層に置く |
| 業務上の事実 | 業務の中で起きた、過去形で表せる出来事。状態の移り変わり、境界の間の約束、操作の結果を、その名前でつなぐ |
| 業務の対象 | 注文、明細、取引先のように、業務で扱い、見分けて記録するもの。何から成り、何で見分けるかを `domain/things.md` に書く |
| 値を入れた見本 | 業務の対象の形の表に添える、値を入れた一件か数件。値は顧客の資料から取り、AI は作らない |
| 画面だけの項目 | 画面に出すが、値がどこから来るのかが見つからない項目と、入力させるが業務の記録にしない項目（検索の語など）。`spec/` に隔離する |
| 業務ルール | 顧客が決める、または合意しなければならない決まり。業務の言葉で書け、決定者が値や選択を決め、破れると業務に損害が出る |
| 判定 | 業務上の問いと、その許される答えの組。判定の中身（どう決めるか）は、決定表などで書く |
| 許される答え | 判定が返しうる答えの集合。一度だけ定義し、状態の移り変わり、受け渡しの約束、操作の結果から引く |
| 受け渡しの約束 | コンテキストの間で、誰が誰に何を渡し、失敗したときにどうするかの約束。通信の方式は含まない |
| 正本 | その事実の唯一の拠り所。正本でないものは、正本から引くか、正本から作る |
| 上流の写し | リポジトリの外にある正本（顧客の要求資料など）を、書き換えずに置いたもの |
| 派生物 | 正本から作った図や文書。道具で生成し、生成し直して差分がないことを確かめられ、先頭に派生物であることを書いたものを置く。表から描く図は、元の表を一行書き、表と同じ変更で描き直すなら、道具で生成しなくても置いてよい |
| スナップショット | 現在の正だけを書いた文書。経緯を含まない |
| 未決事項 | 決める権限を持つ人の判断を待つ問い |
| 設計課題 | 現状のモデルや実装が、あるべき姿とずれている点 |
| ドメイン未定義 | 決まりがないことが、事実である状態。既存のコードに規定がない場合と、決定者が「決まりを置かない」と決めた場合 |
| 決定者 | その事柄を決める権限を持つ人。業務は顧客、範囲はプロダクトオーナー、アーキテクチャはチームのアーキテクト |
| 合意状態 | 顧客と共有する文書の項目に付ける印。仮説、要確認、決定 |
| 仮説 | AI か開発者が書き、まだ誰にも確かめていない項目 |
| 要確認 | 確かめる先と問いが決まっている項目。未決事項を引く |
| 決定 | 決定者が確かめた項目。出所に、決定者と日付か、未決事項への回答か、ワークショップの回を書く |
| 反映待ちの決定事項 | 前の段階で決めたが、反映する段階のブランチがまだない事項。あるべき姿が何段階にもまたがるときに、`questions.md` の節に記録する（[document-system.md](document-system.md) §9） |
| 暫定の決まり | 未決事項の決定を待つ間、作業を進めるために、プロダクトオーナーか開発チームの責任者（単独の責任者がいなければ、チームの合意）が置いた仮の決まり。影響が小さく、元に戻せる事項に限る。合意状態は要確認とし、未決事項を引く（[pattern-language.md](pattern-language.md) §2.1） |
| 変種 | 条件に応じて、既定の文書の組や手順に代えて選ぶもの（[pattern-language.md](pattern-language.md) §2.2） |
| 強制レベル | 不変条件を、モデルがどこまで守っているかの印。強制、表明、外部、不成立、未実装（守るコードがまだない） |
| 記録の線 | 判断を DR に残すかどうかの線。未決事項を解いた判断で、採らなかった選択肢が実際にあり、決定者が記録を求めたもの |
| 判断の節 | スナップショットの中で、直観に反する決まりが、なぜそうなっているかを書く節 |
| 記法の部分集合 | 顧客と共有する文書で使ってよい記法。`AND`、`OR`、任意、複数と、まだ決まっていないことを示す `???` だけを使う（[notation.md](notation.md)） |
| 記法の全体 | 論理モデルで、コードがまだないときに使う記法。操作の入出力、ワークフローなどを含む |
| 論理型 | 業務上の意味を表す属性の型。実装の型とは別に決める |
| 保証 | モデルが実際に守っていること。不変条件の強制レベルで示す |
| 構成要素 | アーキテクチャ設計で、責務とデータを受け持つ単位（モジュールなど） |
| 出来事 | 状態遷移表で、操作と業務上の事実をまとめて呼ぶ語 |
| 生じる事実 | 判定の許される答えごとに、それによって起きる業務上の事実 |
| 現状、あるべき姿 | 現状（as-is）は、いま動いている業務やシステム。あるべき姿（to-be）は、これから作る、または変える姿 |

## 3. 区別する語

| 組 | 区別 |
| --- | --- |
| 業務ルール ↔ 不変条件 | 業務ルールは、顧客が決めるか合意する決まりで、ドメイン設計に置く。不変条件は、モデルが常に成り立たせる性質で、論理モデルに置き、守る業務ルールを識別子で引く。業務ルールに対応しない不変条件もある |
| 判定 ↔ 判断記録 | 判定は、業務の中で繰り返し行われる問いと答え（与信の判定など）。判断記録は、文書や設計の決まりを、決定者が一度決めたことの記録 |
| 仮説 ↔ 決定 | 仮説は、AI や開発者が立てた、確かめる前の記述。決定は、決定者が確かめた記述 |
| 未決 ↔ ドメイン未定義 | 未決は、まだ誰も決めておらず、決める人がいる状態。ドメイン未定義は、決まりがないことが事実である状態 |
| 未決事項 ↔ 設計課題 | 未決事項は、決定者への問い。設計課題は、モデルや実装の歪み |
| 正本 ↔ 派生物 ↔ 上流の写し | 正本は唯一の拠り所。派生物は、正本から作ったもの（道具で生成したものと、表から描いた図）。上流の写しは、外の正本を書き換えずに置いたもの |
| 合意状態 ↔ 強制レベル ↔ 検証 | 合意状態は、誰が決めたか。強制レベルは、モデルが守っているか。検証は、テストで固定されているか。合意済みで、かつ不成立、ということもある |
| 業務の状態 ↔ 合意状態 | 業務の状態は、業務の対象の移り変わり（下書き、確定など）。合意状態は、文書の項目の印 |
| 出来事の記録 ↔ 続いて在るもの | どちらも、業務の対象の種類。出来事の記録は、ある時点に起きたことを記録した対象（注文、見積の依頼など）。続いて在るものは、業務の中で続いて在り、持つ情報が変わっていく対象（取引先、商品など） |
| 境界づけられたコンテキスト ↔ 集約 ↔ 構成要素 ↔ トランザクション ↔ 配置の単位 | どれも別の概念である。その対応は、アーキテクチャ設計で決める |
| ドメインモデル ↔ モデルを記述した文書 | ドメインモデルは、業務の概念と決まりと振る舞いを、実装技術から離れて表した抽象である。文書は、それを書き表したものの一つである |
| モデリング ↔ 文書化 | モデリングは、モデルを見つけて決めること。文書化は、決めたモデルを書き残し、保つこと |
| 現状の記述 ↔ リバースエンジニアリング ↔ 設計 | リバースエンジニアリングは、既存のコードから現状のモデルを復元すること。あるべき姿を決めることとは区別する |

## 4. 単独で使わない語

| 語 | 代わりに |
| --- | --- |
| 設計 | ドメイン設計、アーキテクチャ設計、内部設計のどれか |
| 仕様 | 仕様（外部設計）の層を指すときだけ使う |
| 状態 | 業務の状態、合意状態のどちらか |
| 決定 | 合意状態の「決定」、判定、判断記録のどれか |
| ルール | 業務ルール、不変条件のどちらか |
