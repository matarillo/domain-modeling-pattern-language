# ドメインモデリングと文書化のパターンランゲージ

複雑な業務ルールを持つ IT システムの開発で、ドメインをモデル化し、文書にするためのパターンランゲージである。AI に文書とコードを書かせ、人が判断する開発を前提にする。

- 文書の置き場と単位は [document-system.md](document-system.md)、入口ごとの手順は [processes.md](processes.md)、記法は [notation.md](notation.md)、用語は [glossary.md](glossary.md) にある。
- 既知の手法との関係は [related-methods.md](related-methods.md) にある。この文書のパターンは、筆者の判断である。

## 1. 価値基準

価値基準は、よい・わるいを判定する物差しである。それ自体は行動を指示しない。パターンの採否と、フォースの重みは、これらで説明する。

| 価値基準 | 何を見るか |
| --- | --- |
| 判断の権限 | 決まっていることが、決める権限を持つ人によって決められている。AI や開発者が代わりに決めたことが、決まったことに紛れていない |
| 合意の見分け | 読み手が、決定、仮説、未決を見分けられる |
| 保証の見分け | 読み手が、モデルが守っていることと、守るつもりにすぎないことを見分けられる |
| 現在の正の一意性 | 読み手が、どれが現在の正かで迷わない |
| 二者の読み手 | 人は実装を読まずに業務の構造を理解でき、AI は変更の影響範囲を機械的に特定できる |
| レビュー責任との一致 | 顧客が決めることが、顧客の読む文書にある |
| 正直さ | 書けないこと、決まっていないことが、そうと書かれている。空白が埋めて見せられていない |
| 少ない量と、運用の持続性 | 文書の量が、読み、保守する人の力量に見合っている。AI の作業の費用と、人のレビューの負担が小さい |
| テストへの接続 | 業務ルールが具体例になり、テストとコードの名前に一致している |
| 業務事故の防止 | 間違えると影響が大きいルールと品質に、焦点が当たっている |
| 伝わりやすさ | 読み手が持っている語彙で書かれている |
| 関数型アーキテクチャへの写しやすさ | 操作を「何を受け取り、どの結果（拒否を含む）を返すか」で書ける。判断の記述に、保存や通信の手順が混ざらない（[fsharp-application-design](https://github.com/matarillo/fsharp-application-design)） |
| 業務上の事実を軸にしたデータモデルへの写しやすさ | 業務上の事実（過去形の出来事）を、取消や訂正も含めて、事実の追加として書ける。事実の所有者と、境界の間の約束を書ける（[data-modeling-pattern-language](https://github.com/matarillo/data-modeling-pattern-language)） |

## 2. 大原則

大原則は、価値基準から導かれ、力が対立したときに優先する行動の規則である。番号の小さいものを優先する。

| 原則 | 内容 | 主な価値基準 |
| --- | --- | --- |
| 原則 1 | 決めるのは人である。AI の記述は、合意されるまで仮説である | 判断の権限、合意の見分け |
| 原則 2 | 空白と矛盾は、推測で埋めず、決定者のいる未決事項にする | 判断の権限、正直さ |
| 原則 3 | 顧客が決めることは、顧客が読む文書に置く | レビュー責任との一致 |
| 原則 4 | 一つの事実は一か所に置き、ほかからは識別子で引く | 現在の正の一意性、二者の読み手 |
| 原則 5 | 文書には現在の正だけを書き、経緯は版管理に任せる | 現在の正の一意性 |
| 原則 6 | 現状とあるべき姿を混ぜない | 現在の正の一意性、保証の見分け |
| 原則 7 | 保証されていることと、意図にすぎないことを区別する | 保証の見分け |
| 原則 8 | 扱う論点を絞り、詳細は使う直前に決める | 少ない量と、運用の持続性 |
| 原則 9 | 文書は完成させない。例、コード、テストで確かめて更新する | テストへの接続 |

- 原則 8（量を絞る）は、原則 4〜7（現在の正と保証）より後に置いた。量を減らすために、現在の正や保証の見分けを崩さない。

### 2.1 崩してよいことと、崩してはならない核

原則をそのまま当てはめると重すぎるか、当てはめられないことがある。次の表は、原則ごとに、条件付きで崩してよいことと、どの条件でも崩してはならない核を示す。

| 原則 | 崩してよいこと | 崩してはならない核 |
| --- | --- | --- |
| 原則 1 | 顧客のいない教材や練習の題材では、題材の想定を決定として使ってよい。そのときは、入口の文書に、全体が想定であることを書く | AI の記述を、決定と紛らわしい印や名前で示さない |
| 原則 2 | 決定者と決める時期のある未決事項は、開いたまま、暫定の決まりで作業を進めてよい。暫定にしてよいのは、影響が小さく、元に戻せる事項（表示の順序、文言、元に戻せる操作性など）である。暫定にするかと、暫定の中身は、AI ではなく、プロダクトオーナーか開発チームの責任者が決める。どちらが決めるかは、プロジェクトで決めておく。単独の責任者の役割がないチーム（アジャイルのチームなど）では、チームで合意して決める。決めたら、未決事項に書いて決定者に知らせる。暫定の決まりは、合意状態を要確認にして未決事項を引き、出所に、暫定であることと、置いた人と日付を書く。品質シナリオも、目標の決定者と決める時期があれば、仮の目標を置いて進めてよい | 金銭、監査、権限、個人情報、データの消失、外部との連携の完了条件は、暫定にしない。重要度の最も高い品質シナリオを、目標が未決のまま本番に出さない |
| 原則 3 | 要求・要件が合意されていないうちは、その層を、目的と未決事項だけの薄いままにしてよい。画面だけが持ち、業務ルールとして合意していない決まりは、仕様の層に隔離してよい（[document-system.md](document-system.md) §4.2） | 業務ルールを、内部設計の層に置かない |
| 原則 4 | 同じ対象を、層や観点ごとに書き分けてよい。たとえば業務の状態の移り変わりは、`domain/lifecycles.md` では業務の流れとして、論理モデルでは、モデルが順序を破らない性質として書く。正本から道具で生成した派生物は、印を付けて置いてよい（[document-system.md](document-system.md) §4.4） | 本文を写さない。書き分けた記述は、互いを識別子か名前で引く |
| 原則 5 | 判断記録には、採らなかった案とその理由を残してよい（MP-07）。直観に反する決まりには、現在の理由を判断の節に書いてよい（MP-26） | 変更の前後の対比、移行中の記述、変更の履歴、取り消し線を、文書に残さない |
| 原則 6 | 現状の文書に、現在の判断とその理由を書いてよい。設計課題の台帳に、モデルが守れている部分を書いてよい | 改善の方向とあるべき姿は、設計課題、未決事項、あるべき姿のブランチにだけ置く（MP-17、MP-35） |
| 原則 7 | なし | 表明、外部、不成立の不変条件は、すべて設計課題を持つ。守るコードを確かめていない不変条件を、強制と書かない |
| 原則 8 | リスクを下げるために、開発の準備の期間を先に取ってよい。境界をまたぐ約束が変わるときは、関係者を集めて全体で確かめてよい（MP-30） | 後の機能のための業務の詳細を、前倒しで作らない。準備の期間を、一つの観点（たとえばドメインモデリング）に偏って使わない。目安は 3 分の 1 までで、最大のリスクがはっきりしているときだけ超えてよい |
| 原則 9 | 単純なルールは、例を一つにしてよい（MP-27） | 決定にした記述も、例、コード、テストと矛盾したら、要確認に戻す。記述を直しても、確定した業務上の過去（締めた期間、検収した取引など）は書き換えない。訂正は、新しい事実として扱う（MP-18） |

- 崩してよいかの線は、元に戻せるかと、誤ったときの事故の大きさで引く。元に戻せて影響の小さいものは、決定を待たずに進めてよい。元に戻せず影響の大きいものは、決定を待つか、対象から外す。
- 表にない崩し方をするときは、核に触れないことを確かめる。

### 2.2 条件に応じて選ぶこと

文書の組と手順は、既定を一つ持つ。次の条件に当たるときは、変種を選ぶ。どの変種も、§2.1 の核を崩さない。変種どうしは、組み合わせてよい（例：既存のコードから入り、あるべき姿をブランチで書き、`domain/` を 2 本にする）。

| 調整点 | 既定 | 変種 | 変種を選ぶ条件 | 変種を避ける条件 | 確かめた範囲 |
| --- | --- | --- | --- | --- | --- |
| 入口（[processes.md](processes.md)） | 正本のある所から入る。要求資料と決定者があれば整理された要求から、コードとテストがあれば既存のコードから、要求が固まっていなければワークショップから | 入口を組み合わせる（[processes.md](processes.md) §5） | 既存のシステムを変える。要求から立てた未決事項に、業務の探りが要る。ワークショップで描いた業務を詳しくする | — | 既定：整理された要求と既存のコードからの入口は、題材と AI の試用で確かめた。ワークショップからの入口は、AI の模擬だけである。変種：既存のコードから導いた現状にあるべき姿を足す組み合わせを、AI の試用で確かめた |
| あるべき姿の置き場（[document-system.md](document-system.md) §6.1、§9） | あるべき姿（`to-be`）の文書を本線に置く | 本線の現状（`as-is`）の文書を、ブランチであるべき姿に書き換える（MP-35）。あるべき姿が何段階にもまたがるときは、次の段階だけを書く（[document-system.md](document-system.md) §9） | 既存のシステムの現状を書いた文書がある | — | 変種を AI の試用で確かめた。何段階にもまたがる場合は、確かめていない |
| 前の段階で決めた事項の管理（[document-system.md](document-system.md) §9） | 前の段階で決めた事項は、`questions.md` の「反映待ちの決定事項」の節に記録し、該当する段階のブランチを作るときに文書へ反映する | ワークショップの議事録など、文書体系の外の記録に残し、該当する段階のブランチを作るときに、そこから反映する | 次の三つの要件を満たし、`AGENTS.md` に、記録の置き場と、該当する段階を始めるときに確かめることを明記している。（1）出所の欄から参照できる（URL や識別子が変わらない）。（2）決定者と決定の日付が明記されている。（3）該当する段階に反映するまで、更新されない | 記録が、会話の作成物（ホワイトボードや付箋の写真、図など）だけである。記録の置き場が決まっていない | 確かめていない |
| 文書を足す（[document-system.md](document-system.md) §12） | 最小の構成 | `spec/`、`design/model/`、`decisions/`、`product/quality.md`、コンテキストごとの分割を足す | §12 の表の、それぞれの条件（記録の線を超える最初の判断が出た、要求に品質の要求がある、自分たちで作るコンテキストの構造が複雑である、など） | いつか要るかもしれない、という理由だけで足す（MP-01）。`product/goals.md` の範囲で、既製の製品や外部のサービスで賄うと決めたコンテキストに、`design/model/<コンテキスト>.md` を足す（中の構造は相手が持つ。[document-system.md](document-system.md) §12） | 最小の構成と品質シナリオを、AI の試用で確かめた。既製の製品や外部のサービスで賄うコンテキストの扱いは、確かめていない |
| `domain/` の本数（[document-system.md](document-system.md) §12） | 6 本 | `glossary.md` と、ほかの 5 本を節に分けてまとめた `domain.md` の 2 本 | コンテキストが一つで、業務ルールが少ない | コンテキストが複数ある。受け渡しの約束がある | 確かめていない |
| 上流の正本（[document-system.md](document-system.md) §3） | 写しを `product/upstream/` に置く | 版と所在だけを `product/goals.md` に書く | 機密や形式のために、写しを置けない | 置けるのに置かない（上流の改訂を、写しの差分でたどれなくなる） | 既定を AI の試用で確かめた。変種は確かめていない |
| 業務上の形（MP-28、MP-36、[notation.md](notation.md)） | 表と例で書く。業務の対象の形は、対象ごとに、表と、値を入れた見本で書く | 記法の部分集合のブロックを、表と例に並べる | 選択肢ごとに運ぶ情報が違う | 読み合わせの場がなく、顧客が一人で読む。読み手が記法の読み方で迷った | 仮説。人による確認はない |
| 論理モデルの形（MP-28、MP-29） | コードの型の名前と、論理型の属性の表 | 記法の全体 | 新しいシステムで、コードがまだない | 既存のコードから入る。コードができた後は、既定に置き換える | 既定を AI の試用（既存のコードから入る）で確かめた。変種は確かめていない |
| 例の数（MP-27） | ふつうの例、境界の例、違反の例の三つ | 例を一つ | 単純なルール | 境界の値を持つルール。判定（許される答えごとに例を置く） | 確かめていない |
| アーキテクチャ設計（MP-04、[document-system.md](document-system.md) §10.1） | `architecture/README.md` の七つの節 | ビューや節ごとに文書を足す。または、構成要素と関係のモデルをテキストで一つ置き、図と概観をそこから生成する | 一つの文書で表しきれない。生成するのは、規模が大きく、ビューが多いとき | 生成し直して差分がないことを、道具で確かめられない | 既定を AI の試用で確かめた。変種は確かめていない |
| 図と派生ビュー（[document-system.md](document-system.md) §4.4） | テキストの定義を文書に埋め込む。表から描く図（状態遷移図、コンテキストマップの図、業務の対象の図）は、元の表を一行書いて表のすぐ後に置き、表と同じ変更で描き直す | 正本から生成した派生物を git に置く | 生成、ずれの検出、派生物の印の三つを満たせる | 表から描いたのではない、手で描いた図。AI に作らせたまとめ | 確かめていない |
| コンテキストをまたぐ確定（MP-05、[document-system.md](document-system.md) §10.2） | コンテキストごとに確定する。範囲は、境界どうしの対応の表で決める | 複数のコンテキストの事実を、一つのトランザクションで確定する | 一つのアプリケーションと一つのデータベースで作る | 配置の単位が分かれる | 確かめていない |

- 「確かめた範囲」の意味は、パターンの「確かめた範囲」と同じである。
- 表にない変え方をするときは、§2.1 の核に触れないことを確かめる。

### 第 1 部 文書体系

### MP-01 問いで決める文書の組 ★

**文脈**：モデリングの手法は、それぞれ作成物を持つ。AI は、それらを網羅的に作ることをためらわない。このパターンは、文書体系の全体を決める最初のパターンである。

**問題**：**手法や工程が求める作成物を並べていくと、文書の数が、読み、保守する人の手に余り、やがて更新されなくなる。**

**フォース**
- 手法ごとの作成物には、それぞれ理由がある。
- 文書が増えるほど、どれが現在の正かを保つ手間が増える。
- AI は量を作れるが、人のレビューの量は増やせない。

**解決**：したがって、文書を作成物からではなく、その文書が答える問いから決めよ。問いごとに一つの文書を置き、入口の文書に、問いの一覧と読む順を書く。新しく分かったことは、既存の文書の問いに当てはめて追記し、どの問いにも当たらないものだけ、新しい文書を考える。

**結果として生じる文脈**：文書の数が問いの数に絞られる。次に、問いを層と観点に分ける（MP-02、MP-03）。

**事例**
- `[ddd-business-sample@70819ae example01-b2b-order-to-cash/docs/00_readme.md]` は、扱う問いを入口で宣言し、文書を増やさずに追記する運用を書いている。

**確かめた範囲**：パターンを導いた題材で現れている。AI による試用（例題、整理された要求から入る手順）でも、機能に要る文書だけが作られた。（人に関わる）

**関連する既知の手法**：—

**主な価値基準と原則**：少ない量と運用の持続性、二者の読み手／原則 8

### MP-02 答える問いで分けた層 ★

**文脈**：MP-01 で決めた文書を、どこに置くかを決める。開発の工程は、要求から実装へ順に進むように語られることが多い。

**問題**：**文書を工程の順に並べると、どの文書を誰がレビューし、何が変わったら直すのかが、工程の名前からは読み取れない。**

**フォース**
- 工程の順は、新しい人に分かりやすい。
- 実際の開発は、一つの機能を縦に薄く作り、必要な文書だけを直す。
- 顧客が読む範囲と、チームだけが読む範囲を、はっきりさせたい。

**解決**：したがって、文書を、答える問いで層に分けよ。要求（なぜ作るのか）、要件（何を引き受けるのか）、仕様（外部設計。外からどう見えるか）、内部設計（内部をどう作るか）の四つとし、層ごとに、誰の言葉で書き、誰が決め、顧客がレビューするかを定める。層は工程ではないので、順に埋めず、フォルダに番号を振らない。

**結果として生じる文脈**：レビューの範囲と更新の理由が、層から分かる。ただし、層を横断する理解の置き場が要る（MP-03）。

**事例**
- `[bobs-used-bookstore-sample@de81fc8 docs/README.md]` は、四つの層を問い、主語、誰の言葉か、変わる理由で定義している。

**確かめた範囲**：パターンを導いた題材で現れている。（人に関わる）

**関連する既知の手法**：—

**主な価値基準と原則**：レビュー責任との一致、現在の正の一意性／原則 3

### MP-03 層を横断する共有の理解 ★★

**文脈**：MP-02 で層を分けた。ドメインの理解（言葉、境界、業務上の事実、業務ルール、状態の移り変わり）は、要求にも、仕様にも、内部設計にも現れる。

**問題**：**ドメインの理解を層ごとに分けて置くと、境界や業務上の事実のように、顧客と共有するが外部の仕様ではないものの置き場がなくなり、入口によって違う場所に書かれる。**

**フォース**
- 顧客がレビューする範囲は、はっきりさせたい（原則 3）。
- 整理された要求、既存のコード、ワークショップのどこから入っても、同じ文書が残ってほしい。
- 集約や強制レベルのように、技術に依存しないが顧客と共有しないものもある。

**解決**：したがって、顧客と開発チームが共有するドメインの理解を、層から独立した置き場（ドメイン設計）に集めよ。そこには、顧客と共有するものだけを置く。技術に依存しないが顧客と共有しない論理モデルは、内部設計の層に置く。アーキテクチャ設計も、層から独立した置き場に置く（MP-04）。

**結果として生じる文脈**：どの入口からも、ドメイン設計の同じ文書に書く。顧客のレビューの範囲は、フォルダで分かる。ドメイン設計の中身は、業務上の事実（MP-18）、境界（MP-19）、判定（MP-22）、状態遷移（MP-23）、用語（MP-24）で書く。業務ルールと不変条件の線を引く必要が生じる（MP-21）。

**事例**
- 例題では、要求資料から、用語、事実、業務ルール、状態遷移、境界の案を、すべて `domain/` に書く（[document-system.md](document-system.md) §11）。

**確かめた範囲**：AI による試用（例題、整理された要求から入る手順）、AI による試用（題材と同じコードから入る手順）、AI どうしのワークショップの模擬（例題。弱い証拠）のどれでも、顧客と共有する理解が `domain/` の同じ文書に書かれた。

**関連する既知の手法**：—

**主な価値基準と原則**：レビュー責任との一致、伝わりやすさ／原則 3、原則 4

### MP-04 入口から育てるアーキテクチャ設計

**文脈**：アーキテクチャ設計（方式設計）は、設計条件、方針、システムの境界、構成要素、実行と配置、横断的な方式、品質の評価を扱う。規模によって、必要な量が大きく違う。

**問題**：**アーキテクチャ設計の書き方を最初に決め打ちすると、規模に合わない。細かく分ければ、書くことのない文書とドメイン設計の言い換えが増え、一つの文書に押し込めば、ビューが育ったときに表しきれない。**

**フォース**
- 小さなシステムでは、数行で足りる節が多い。
- 大きなシステムでは、図を含むビューが、人の理解に欠かせない。
- アーキテクチャ設計が、ドメイン設計の境界や規則を言い換えると、食い違いが生まれる。

**解決**：したがって、アーキテクチャ設計に専用のディレクトリを用意し、入口の一つの文書に、七つの節（概要・設計条件、基本方針、システムコンテキスト、論理アーキテクチャ、実行時・配置、横断的な方式、品質評価・リスク）の最小の中身を書くことから始めよ。書くことのない節には、ないことを 1 行で書く。ビューや節が育ったら、同じディレクトリに文書を足して入口から引く。ドメイン設計に書いたことは言い換えず、識別子で引く。

**結果として生じる文脈**：アーキテクチャ設計は、規模に合わせて育つ。境界どうしの対応を、ここで決める（MP-05）。図の扱いは MP-06 に従う。

**事例**：—

**確かめた範囲**：AI による試用（例題、整理された要求から入る手順）で、入口の文書に七つの節の最小の中身を書けた。ビューが育つ規模では、確かめていない。

**関連する既知の手法**：arc42 の節 [Hruschka and Starke n.d.]、C4 モデルの図の水準 [Brown n.d.a]

**主な価値基準と原則**：少ない量と運用の持続性、現在の正の一意性／原則 4、原則 8

### MP-05 境界どうしの対応を一か所で決める

**文脈**：境界づけられたコンテキスト、集約、構成要素、トランザクション、配置の単位、チームは、どれも「境界」と呼ばれる。ドメインの資料は、コンテキストの間を非同期のイベントで結ぶことを前提に語ることが多い。

**問題**：**コンテキストの境界を、トランザクションや配置の境界と同じものとして書くと、一つのアプリケーションと一つのデータベースで作る場合でも、ドメインの記述が非同期の連携や補償の手順を前提にしてしまう。**

**フォース**
- コンテキストの境界は、言葉とモデルの一貫性で決まる。
- トランザクションの範囲と配置の単位は、技術と運用の条件で決まる。
- 業務は、境界をまたぐ結果がいつそろうかを気にすることがある。

**解決**：したがって、境界どうしの対応（どのコンテキストを、どの構成要素で、どのトランザクションの範囲で、どこに置き、どのチームが持つか）を、アーキテクチャ設計の一つの表で決めよ。ドメイン設計は、特定の対応を前提にしない。業務が結果のそろう時間を気にするときだけ、それを業務ルールとして書く。

**結果として生じる文脈**：ドメイン設計は、配置の方式が変わっても書き直さずに済む。不変条件の強制レベル（MP-13）は、この表の確定の範囲を前提にする。

**事例**：—

**確かめた範囲**：AI による試用（例題、整理された要求から入る手順）で、対応の表を置き、決まっていない欄を未決事項にした。対応を実際に決める場面では、確かめていない。

**関連する既知の手法**：集約の境界の外を結果整合にする規則 [Vernon 2011b] は、集約についての規則である。コンテキストの間の確定の範囲は、この表で選ぶ。受け持つチームの欄の書き方は、一つのコンテキストを一つのチームだけが持ち、一つのチームは複数を持てる、という考え [Kaiser 2023] に従う。

**主な価値基準と原則**：関数型アーキテクチャへの写しやすさ、業務上の事実を軸にしたデータモデルへの写しやすさ／原則 4

### MP-06 現在版だけを持つ ★

**文脈**：文書は、コードや合意の変化に合わせて直される。AI に書かせると、変更のたびに旧版との対比や改訂の注記が残りやすい。

**問題**：**時点ごとの版や、変更の前後の記述が文書の中に並ぶと、読み手はどれが現在の正かを自分で判断しなければならず、AI は古い記述を前提に変更する。**

**フォース**
- 変更の理由は、後で知りたくなる。
- 過去の版は、版管理がすでに持っている。
- 人の理解のための図やまとめは、正本の写しになりやすい。

**解決**：したがって、文書には現在の正だけを、最初からそうであったかのように書け。変更の理由はコミットのメッセージに書き、過去の版はタグやコミットで指す。図は、テキストの定義で埋め込むか、正本から道具で生成し、生成し直して差分がないことを確かめられるものだけを、派生物と明記して置く。表から描く図は、元の表を書き、表と同じ変更で描き直すなら、表のすぐ後に置いてよい（[document-system.md](document-system.md) §4.4）。人がレビューするために AI が生成した点検の結果は、常設の文書にせず、レビューの場に置く。

**結果として生じる文脈**：どの文書も一つの現在版を持つ。理由を残すべき判断は、判断記録に分ける（MP-07）。

**事例**
- `[bobs-used-bookstore-sample@d89f591 AGENTS.md]` は、文書に最新のスナップショットだけを書き、経緯を書かない規律を定めている。

**確かめた範囲**：パターンを導いた題材で現れている。

**関連する既知の手法**：—

**主な価値基準と原則**：現在の正の一意性、二者の読み手／原則 5

### MP-07 線を超える判断だけを記録する

**文脈**：MP-06 で、文書から経緯を除いた。しかし、採らなかった案とその理由がどこにもなければ、同じ議論が繰り返される。AI は、退けられた案を何度でも提案しうる。

**問題**：**判断をすべて記録すると、記録は読まれず、文書の内容と食い違う。何も記録しないと、同じ議論が繰り返される。**

**フォース**
- 決めた内容の正本は、文書にあるべきである。
- 採らなかった案は、文書には書けない。
- 記録するかどうかを AI が決めると、AI の判断が記録に紛れる。

**解決**：したがって、未決事項を解いた判断のうち、採らなかった選択肢が資料や会話に実際にあり、決定者が記録を求めたものだけを、判断記録にせよ。影響の大きい領域（金銭、監査、権限、個人情報、データの消失、外部連携の完了条件など）では、記録を求めることを既定にする。判断記録には、題、種別、有効性、問いの要旨、反映した項目、理由、採らなかった案だけを書き、決めた内容は反映した項目を正本とする。AI は、人が下した判断を書き起こしてよいが、自分の判断を記録にしない。

**結果として生じる文脈**：判断記録は少なく保たれ、文書を読むのに判断記録を読む必要がない。文書を正しく読むための現在の理由は、文書の中の判断の節に置く（MP-26）。

**事例**：—

**確かめた範囲**：AI による試用（題材と同じコードから導いた文書に、あるべき姿を足す手順）で、決定者が記録を求めた判断だけが判断記録になった。記録の線そのものを、決定者が使う場面では確かめていない。

**関連する既知の手法**：ADR [Nygard 2011]、MADR [ADR 2024]。記録を ADR に限らず、記録の線で絞る点が違う。判断ごとの記録を標準にしない [fsharp-application-design](https://github.com/matarillo/fsharp-application-design) の方針とは対立する（[related-methods.md](related-methods.md) §4）。

**主な価値基準と原則**：判断の権限、少ない量と運用の持続性／原則 1、原則 5

### MP-08 判断記録を種別で呼び分ける

**文脈**：MP-07 で判断記録を残すことにした。判断記録の形式は、アーキテクチャの判断の記録（ADR）として広まっている。

**問題**：**判断記録の形式がアーキテクチャの記録として広まっているため、業務の判断もアーキテクチャの記録として並び、アーキテクチャ設計が引くべき有効な判断が、業務の判断に埋もれる。**

**フォース**
- 記録の形式は一つにそろえたい。
- アーキテクチャ設計は、現在有効で重要な判断だけを引きたい。
- 業務の判断の決定者は顧客、アーキテクチャの判断の決定者はチームである。

**解決**：したがって、判断・意思決定の記録を判断記録（DR）と呼び、一つの置き場と一つの接頭辞にそろえ、種別（業務、範囲、アーキテクチャなど）で呼び分けよ。ADR は、種別がアーキテクチャの判断記録だけを指す。判断記録は、有効か置き換え済みかを持ち、アーキテクチャ設計は有効で重要な ADR だけを引く。

**結果として生じる文脈**：業務の判断とアーキテクチャの判断が、同じ形式で、種別によって引き分けられる。

**事例**：—

**確かめた範囲**：AI による試用（題材と同じコードから導いた文書に、あるべき姿を足す手順）で、種別を付けた判断記録が一件書かれた。アーキテクチャの判断記録との引き分けは、確かめていない。

**関連する既知の手法**：MADR は、アーキテクチャ以外の判断も記録できるとしている [ADR 2024]。

**主な価値基準と原則**：現在の正の一意性、判断の権限／原則 1

### MP-09 識別子で一か所を引く ★★

**文脈**：MP-02、MP-03 で文書を分けると、同じ事実が複数の文書に関わる。

**問題**：**事実の本文を文書の間で写すと、片方だけが変わって食い違い、AI もどちらが正かを判断できない。**

**フォース**
- 読み手は、一つの文書で完結して読みたい。
- 写した本文は、元が変わっても追いかけられない。
- AI は、識別子なら機械的にたどれる。

**解決**：したがって、一つの事実を一か所でだけ定義し、ほかの文書からは識別子で引け。接頭辞は体系の中で一つの意味だけを持たせ、一覧を入口の文書に置く。変更の依頼、課題の報告、AI への指示でも、識別子で対象を指す。識別子の番号は再び使わない。リポジトリの外にある上流の正本（顧客の要求資料など）は、書き換えない写しとして置く。写しが正であるのは、上流がその版で何を求めたかについてである。このプロジェクトが決める事柄と、変えていく事柄は、写しから読み取って、種類ごとの置き場に項目として書き、出所に写しの箇所を書く。その事柄の現在の正は、項目である。上流が決め続け、このプロジェクトが従うだけの事柄は、写しに残して、使う所から引く。

**結果として生じる文脈**：変更の影響範囲を、識別子からたどれる。同じ事実が書かれやすい組み合わせについては、どちらを正本にするかを決めておく（[document-system.md](document-system.md) §4.3）。

**事例**
- `[bobs-used-bookstore-sample@de81fc8 docs/README.md]` は、層ごとの接頭辞を一覧にしている。`[ddd-business-sample@70819ae example01-b2b-order-to-cash/models/20_credit.md]` は、不変条件からルールの識別子を引いている。

**確かめた範囲**：パターンを導いた題材で現れている。AI による試用（例題、整理された要求から入る手順）で、業務ルール、判定、未決事項、品質シナリオが識別子で引き合った。上流の写しのうち、どこまでを項目に書き、どこを写しに残すかの分け方は、確かめていない。

**関連する既知の手法**：—

**主な価値基準と原則**：現在の正の一意性、二者の読み手／原則 4

### MP-10 二者の読み手のための入口 ★

**文脈**：文書には、人の理解を助ける役割と、AI の入力になる役割がある。

**問題**：**人向けに書いた文書は、AI が変更の影響範囲をたどる手がかりにならず、AI 向けの索引は、人に業務の構造を伝えない。**

**フォース**
- 二種類の文書を作ると、量が増え、食い違う。

**解決**：したがって、一つの文書体系に、二者の入口を置け。入口の文書に、読み手の目的ごとの読む順を書き、AI 向けには、作業の規律を `AGENTS.md` に書く。影響範囲を特定する入口（識別子の一覧と、強制レベルごとの件数）を、両者が共有する。

**結果として生じる文脈**：人と AI が、同じ正本を読む。どの記述がどこまで確かかを、印で示す（MP-11）。

**事例**
- `[bobs-used-bookstore-sample@de81fc8 docs/README.md]` は、読み手ごとの入口を表にしている。

### MP-11 軸ごとの確かさの印 ★★

**文脈**：MP-10 で、人と AI が同じ正本を読むようにした。文書の記述には、決まったもの、AI の案、モデルが守っているもの、守るつもりのもの、テストで固定されているものが混ざる。

**問題**：**「確定」「済み」のような一つの印では、決定者が認めたのか、モデルが守っているのか、テストで固定されているのかが読み取れず、AI は合意しただけの決まりを、守られている保証として扱う。**

**フォース**
- 印が少ないほど、文書は軽い。
- 合意していても、モデルが守っていないことがある。
- 導出元（要求か、コードか、ワークショップか）と時点（現状か、あるべき姿か）も、読み方を変える。

**解決**：したがって、確かさを軸ごとに別の印で持て。文書の単位では、導出元と時点を書く。項目の単位では、顧客と共有する項目に合意状態（MP-12）、不変条件に強制レベル（MP-13）、業務ルールと不変条件に検証の有無（MP-14）を付ける。

**結果として生じる文脈**：読み手は、軸ごとに確かさを読める。各軸の印は、MP-12〜MP-14 で決める。

**事例**：—

**確かめた範囲**：AI による試用（例題、整理された要求から入る手順）で、導出元、時点、合意状態を分けて付けた。AI による試用（題材と同じコードから入る手順）で、強制レベルと検証を付けた。

**関連する既知の手法**：—

**主な価値基準と原則**：合意の見分け、保証の見分け／原則 1、原則 7

### MP-12 項目ごとの合意状態 ★

**文脈**：MP-11 の合意の軸。AI は、要求資料やコードから、もっともらしい記述を大量に書く。

**問題**：**AI が書いた項目と、決定者が合意した項目が、同じ表に同じ書き方で並ぶと、読み手は全部を決まったことと読む。**

**フォース**
- 顧客と共有する項目のすべてに印を付けるのは、手間がかかる。
- 平易に見える記述ほど、顧客は分からないまま「よい」と言いやすい。
- 決めるのは人である（原則 1）。

**解決**：したがって、ドメイン設計と、要求・要件の文書のすべての項目に、合意状態（仮説、要確認、決定）を付けよ。決定の印は、人の判断が記録に残っているときだけ付け、出所に決定者と日付を書き、未決事項への回答やワークショップの回で決めたなら、それも書く。AI が決定の印を書くのは、記録に残った人の判断を写すときに限る。要約の読み上げに同意を得たときは、要約がはっきり指した項目だけを決定にする。業務の対象の形の表と、記法で書いた形に決定の印を付けるのは、読み合わせの場で、顧客が問い（[notation.md](notation.md) §3.3）に答えた後に限る。

**結果として生じる文脈**：読み手は、決まったことと AI の案を見分けられる。要確認の項目は、未決事項につながる（MP-15）。

**事例**
- `[ddd-business-sample@70819ae example01-b2b-order-to-cash/docs/05_domain_rules_and_lifecycles.md]` は、重要なルールごとに、仮説、要確認、決定の合意状態を持つ。

**確かめた範囲**：パターンを導いた題材で現れている。人の決定者による読み合わせでは、確かめていない。（人に関わる）

**関連する既知の手法**：描いたものを最初から語り直して同意を得る進め方 [Hofer and Schwentner 2026a]。定式化した記述を「自分ならこう書いたか」で確かめる運用 [Wynne 2015]。

**主な価値基準と原則**：判断の権限、合意の見分け／原則 1

### MP-13 不変条件の強制レベル ★

**文脈**：MP-11 の保証の軸。論理モデルには、「集約が守る」と書かれた不変条件が並ぶ。

**問題**：**モデルが実際に守っている条件と、守るつもりで守っていない条件が、同じ書き方で並ぶと、AI は存在しない保証を前提にコードを変える。**

**フォース**
- 不変条件は、意図として書かれることが多い。
- どこまで守っているかを調べるには、コードを読む必要がある。
- 守られていない条件は、直すべき課題でもある。

**解決**：したがって、不変条件ごとに、強制レベル（強制、表明、外部、不成立、未実装）を付けよ。強制レベルごとの件数を文書に書き、表明、外部、不成立のものには、是正の扱いと、対応する設計課題（MP-17）を付ける。守るコードがまだない不変条件は「未実装」とし、不具合の「不成立」と分ける。顧客が決めた業務ルールを守る不変条件が「不成立」なら、未決事項も立てる。

**結果として生じる文脈**：AI と人は、保証と意図を見分けられる。強制レベルは、トランザクションの範囲（MP-05）を前提にする。

**事例**
- `[bobs-used-bookstore-sample@de81fc8 docs/design/domain/invariants.md]` は、すべての不変条件に強制レベルを付け、件数を集計している。

**確かめた範囲**：パターンを導いた題材で現れている。AI による試用（題材と同じコードから入る手順）でも、強制でない不変条件のすべてが設計課題に対応した。

**関連する既知の手法**：不変条件と是正の方針を対で書く [DDD Crew 2022]

**主な価値基準と原則**：保証の見分け／原則 7

### MP-14 テストで固定された範囲 ★

**文脈**：MP-11 の検証の軸。業務ルールや不変条件の一部は、自動テストで固定されている。

**問題**：**文書の記述のうち、どれが自動テストで固定されているかが見えないと、変更したあとに、どの業務ルールや不変条件が破れても気づけるのかを、誰も判断できない。**

**フォース**
- テストの一覧を文書に写すと、コードの言い換えになる。
- テストとルールの対応は、変更のたびに変わる。
- 固定されていない記述こそ、変更のときに危ない。

**解決**：したがって、業務ルールと不変条件の項目に、自動テストで固定されているか（あり／なし）だけを書け。どのテストが固定しているかは、テストの名前にルールや不変条件の識別子を入れ、道具で一覧にする。固定されていない記述を、そうと見えるようにする。

**結果として生じる文脈**：変更の前に、固定されていない範囲が分かる。既存のコードを直すときは、先に挙動を固定する（MP-33）。

**事例**
- `[bobs-used-bookstore-sample@de81fc8 docs/design/domain/verified-by-test.md]` は、テストで固定された範囲と、固定されていない範囲を分けて書いている。

**確かめた範囲**：パターンを導いた題材で現れている（独立した文書の形）。項目の列に畳む形は、AI による試用（題材と同じコードから入る手順）で書けた。

**関連する既知の手法**：—

**主な価値基準と原則**：保証の見分け、テストへの接続／原則 7、原則 9

### MP-15 決定者つきの未決事項 ★★

**文脈**：要求資料にも、既存のコードにも、ワークショップの会話にも、空白と食い違いがある。AI は、空白をもっともらしく埋める。

**問題**：**決まっていないことを放置すると、実装の時点で、誰かが黙って決めてしまう。**

**フォース**
- 未決事項を挙げ続けると、一覧が膨らむ。
- 決める人と時期が分からない問いは、誰も答えない。
- 低い危険の事項まで止めると、開発が進まない。

**解決**：したがって、空白と矛盾を、一つの問いずつ、決定者と決める時期を持つ未決事項にし、入口を問わず一つの台帳に置け。要求にない数値や基準を、推測で補わない。業務の値と基準は補わないが、モデルの案は仮説として書いてよい。決まったら、項目を直して決定の印を付け、台帳から消す。

**結果として生じる文脈**：決める人と時期のある問いだけが残る。規定がないことが事実なら、未決ではなくドメイン未定義として書く（MP-16）。

**事例**
- `[ddd-business-sample@70819ae example01-b2b-order-to-cash/docs/07_open_questions.md]`、`[bobs-used-bookstore-sample@de81fc8 docs/product/open-questions.md]` は、確認先と時期を持つ未決事項の台帳である。
- 例題の要求資料は、限度額を超える注文を、ある節では「断る」、別の節では「審査する」と書いている。これは、推測で選ばず、未決事項にする。

**確かめた範囲**：パターンを導いた題材で現れている。AI による試用（例題、整理された要求から入る手順）で、要求資料の食い違いと、判定の入力の空白を、未決事項にした。

**関連する既知の手法**：ホットスポット [Avanscoperta 2025a]、質問カード [Wynne 2015]、不確かな箇所の印 [Brandolini 2009]

**主な価値基準と原則**：判断の権限、正直さ、業務事故の防止／原則 2

### MP-16 取り決めがないことを書く ★

**文脈**：既存のコードから文書を導くと、コードに規定のない事項が多く見つかる。

**問題**：**規定のないことを書かずに済ませると、読み手は「規定がない」のか「書き漏れ」なのかを区別できず、AI は自分で補う。**

**フォース**
- 書いていないことは、ないことと同じに見える。
- 規定がないことと、まだ決めていないことは違う。
- すべての「ない」を書くと、量が増える。

**解決**：したがって、決まりがないことが事実である事項を、「ドメイン未定義」と書け。ルールがない領域は業務ルールの文書に、モデルが規定しない事項は論理モデルに書く。まだ誰も決めていないだけなら、ドメイン未定義ではなく未決事項にする（MP-15）。決めるべきだと分かったら、未決事項を立てる。

**結果として生じる文脈**：読み手と AI は、規定がないことを事実として扱える。

**事例**
- `[bobs-used-bookstore-sample@de81fc8 docs/spec/rules.md]` は、ルールが存在しない領域を節にしている。

**確かめた範囲**：パターンを導いた題材で現れている。AI による試用（題材と同じコードから入る手順）でも、コードに規定のない領域を、未決事項と分けて書いた。

**関連する既知の手法**：—

**主な価値基準と原則**：正直さ／原則 2

### MP-17 現状と課題を分ける ★

**文脈**：既存のコードから現状のモデルを導くと、歪みや改善の案が見つかる。

**問題**：**見つけた歪みと改善の案を、現状の記述の中に書くと、どこまでが事実で、どこからがあるべき姿かが分からなくなる。**

**フォース**
- 改善の案は、見つけたその場で書き留めたい。
- 現状の記述は、事実だけであってほしい。
- 歪みと、決定者への問いは、扱う人が違う。

**解決**：したがって、現状の記述には事実だけを書き、歪みと改善の方向は、設計課題の台帳に隔離せよ。台帳の項目は、識別子、重大度、関係する識別子、現象、影響、改善の方向を持つ。決定者への問いは、設計課題ではなく未決事項にする。

**結果として生じる文脈**：現状の記述が事実に保たれる。あるべき姿をまとめて設計するときは、MP-35 に従う。

**事例**
- `[bobs-used-bookstore-sample@de81fc8 docs/design/issues.md]` は、設計課題を一つの台帳にしている。

**確かめた範囲**：パターンを導いた題材で現れている。AI による試用（題材と同じコードから入る手順）でも、歪みを現状の記述から分けた。

**関連する既知の手法**：—

**主な価値基準と原則**：現在の正の一意性、保証の見分け／原則 6

### MP-18 業務上の事実を背骨にする ★★

**文脈**：MP-03 で、顧客と共有する理解を一つの置き場に集めた。ドメイン設計には、業務の流れ、状態の移り変わり、境界の間の受け渡し、操作の結果が書かれる。手法ごとに、出来事、遷移を起こすもの、メッセージ、帰結など、違う名前で呼ばれる。

**問題**：**同じ業務上の出来事が、文書ごとに違う名前で書かれると、状態遷移、受け渡し、操作の結果が同じ出来事を指していることが分からず、手法の間でつながらない。**

**フォース**
- 業務の人は、出来事を過去形で語りやすい。
- 取消や訂正は、元の出来事を消すのではなく、新しい出来事として起きる。
- 出来事の一覧を作ると、文書が一つ増える。

**解決**：したがって、業務上の事実（過去形の出来事）の一覧を一つ作り、どのコンテキストで起き、何を運ぶかを書け。状態遷移表の出来事、受け渡しの約束、操作の結果は、その名前を引く。取消や訂正は、元の事実を引く新しい事実として書く。主な流れは、事実の並びとして書く。

**結果として生じる文脈**：出来事を軸に、状態、境界、判定がつながる。状態遷移表（MP-23）と判定（MP-22）は、この名前を使う。

**事例**
- 例題では、判定の答え「自動で承認する」から生じる事実「与信が承認された」を、状態遷移表の出来事と、受け渡しの約束の運ぶものが、同じ名前で引く。

**確かめた範囲**：AI による試用（例題、整理された要求から入る手順）で、状態遷移表の出来事と、受け渡しの約束の運ぶものが、事実の一覧の名前を引いた。

**関連する既知の手法**：過去形の出来事を時系列に並べる [Brandolini 2013]、業務上の事実を分類するデータモデル（[data-modeling-pattern-language](https://github.com/matarillo/data-modeling-pattern-language)）

**主な価値基準と原則**：業務上の事実を軸にしたデータモデルへの写しやすさ、二者の読み手／原則 4

### MP-19 業務ルールの一貫性で切る境界 ★

**文脈**：MP-03 で、境界をドメイン設計に置くことにした。要求資料は、画面、要件の番号、担当の役割で区切られていることが多い。境界づけられたコンテキストを、どこで切るかを決める。

**問題**：**要求資料の章や画面の区切りに合わせて境界を引くと、同じ言葉や状態を複数の責任が使い回し、その意味が少しずつずれていく。**

**フォース**
- 要求資料の区切りは、顧客にとって自然である。
- 一緒に変わるルールが別の境界に分かれると、変更のたびに両方を直す。
- 境界を細かくしすぎると、受け渡しが増える。

**解決**：したがって、次のものが同時に変わる所を、境界の候補にせよ。最終的な判断の責任者、言葉の意味と状態の移り変わり、同時に正しく保つべきルール、変わる理由と頻度、外部との約束。業務全体で一つのステータスを共有している所は、責任ごとの状態の移り変わりに分ける。

**結果として生じる文脈**：境界の間の受け渡しを決める（MP-20）。境界と構成要素の対応は、アーキテクチャ設計で決める（MP-05）。

**事例**
- `[ddd-business-sample@70819ae example01-b2b-order-to-cash/docs/03_bounded_contexts.md]` は、責任、持つ情報、持たない責任で境界を定めている。

**確かめた範囲**：パターンを導いた題材で現れている。AI による試用（例題、整理された要求から入る手順）で、境界の案を仮説として立てた。（人に関わる）

**関連する既知の手法**：境界の候補を、ドメインエキスパートに示してもらう問い [Hofer and Schwentner 2021]

**主な価値基準と原則**：伝わりやすさ、業務事故の防止／原則 3

### MP-20 失敗時の扱いを含む受け渡しの約束 ★★

**文脈**：MP-19 で境界を切った。境界の間では、情報が受け渡される。

**問題**：**境界の間で渡す情報だけを決めると、遅れ、重複、欠落、一部の失敗のときに、どちらが何をするかが決まらない。**

**フォース**
- 通信の方式は、まだ決めたくない。
- 失敗の扱いは、業務の判断を含む。
- 受け手が送り手の内部を直接書き換えると、境界が崩れる。

**解決**：したがって、受け渡しごとに、送り手、受け手、運ぶ情報、重複を見分ける鍵、失敗したときの扱いを、表で約束せよ。通信の方式は書かない。受け手は、送り手の内部の状態を直接書き換えない。

**結果として生じる文脈**：境界の間の失敗が、業務の言葉で決まる。届く事実は、状態遷移表の行になる（MP-23）。

**事例**
- `[ddd-business-sample@70819ae example01-b2b-order-to-cash/docs/04_context_map.md]` は、受け渡しごとに、必須の情報、重複を見分ける鍵、失敗したときの扱いを表にしている。

**確かめた範囲**：パターンを導いた題材で現れている。AI による試用（例題、整理された要求から入る手順）で、受け渡しごとに失敗の扱いを書き、届かないときの業務の扱いを決めた。

**関連する既知の手法**：関係のパターン [Evans 2015]、問いごとの小さなマップ [Brandolini 2009]、利用者の側から書く約束 [Robinson 2006]

**主な価値基準と原則**：業務事故の防止、関数型アーキテクチャへの写しやすさ／原則 2

### MP-21 業務ルールと不変条件を分ける ★

**文脈**：MP-03 で、顧客と共有するものと、論理モデルを分けた。決まりには、顧客が決めるものと、モデルが守る性質がある。

**問題**：**業務ルールと、モデルが守る性質を一つの一覧に並べると、顧客が決めるべきことが設計の中に埋もれ、顧客のレビューから漏れる。**

**フォース**
- 同じ決まりが、業務ルールとしても不変条件としても書けることがある。
- 「何と何を同時に正しく保つか」は、顧客の要求である。
- 集約や強制レベルは、顧客の知識ではない。

**解決**：したがって、業務の言葉で書け、決定者が値や選択を決め、破れると業務に損害が出る決まりを、業務ルールとしてドメイン設計に置け。不変条件は、論理モデルに、それをモデルがどう守るかを強制レベル付きで書き、守る業務ルールを識別子で引く。業務ルールに対応しない不変条件も認める。

**結果として生じる文脈**：顧客は業務ルールだけを読めばよく、チームは不変条件で保証を確かめられる。

**事例**
- `[bobs-used-bookstore-sample@de81fc8 docs/spec/rules.md]` と `[bobs-used-bookstore-sample@de81fc8 docs/design/domain/invariants.md]` は、業務ルールと不変条件を分け、互いの分担を冒頭で宣言している。

**確かめた範囲**：パターンを導いた題材で現れている。ただし線の引き方（三つの問い）は題材と違い、AI による試用（題材と同じコードから入る手順）で当てはめた。

**関連する既知の手法**：「それは誰の仕事か」と問い、整合の要求を業務の言葉で聞く [Vernon 2011b]、[Wlaschin 2024 §5.8]。業務ルールを宣言的な文で書く [Business Rules Group 2003]

**主な価値基準と原則**：レビュー責任との一致、保証の見分け／原則 3、原則 7

### MP-22 判定と許される答えを一度だけ定義する ★★

**文脈**：業務には、与信の判定のように、複数の条件から答えを決める判断がある。その答えは、状態遷移、受け渡し、操作の結果に現れる。

**問題**：**判定が状態遷移や操作の手順の中に埋もれていると、何を問い、どんな答えがありうるかが見えず、答えの集合が文書ごとに食い違う。**

**フォース**
- 判定の中身（どう決めるか）は、まだ決まっていないことが多い。
- 答えの集合は、早く決めたい。状態と受け渡しが、それに依存する。
- 確かめる順序を書くと、手順と依存が混ざる。

**解決**：したがって、判定ごとに、問い、入力（どの値をどの定義で使うか）、許される答えを、業務ルールの文書で一度だけ定義せよ。中身は、決まったら決定表で書く。確かめる順序は書かず、入力への依存だけを書く。許される答えごとに、それによって生じる業務上の事実の名前を書く。状態遷移表と受け渡しの約束はその事実の名前を、操作の結果は許される答えの名前を引く。

**結果として生じる文脈**：答えの集合が一つに保たれる。答えは、関数型の設計では、結果の型の選択肢になる（MP-28）。

**事例**
- 例題の与信の判定は、問い、入力、許される答え（自動で承認する、与信担当者が審査する、断る）を先に定義し、決定表で中身を書く（[notation.md](notation.md) §2.2）。

**確かめた範囲**：AI による試用（例題、整理された要求から入る手順）で、判定の問い、入力、許される答えを定義し、入力の定義の空白を未決事項にした。

**関連する既知の手法**：決定、問い、許される答え [Taylor 2023b]、依存であって順序ではない [Taylor 2023a]、決定表 [OMG 2024]

**主な価値基準と原則**：関数型アーキテクチャへの写しやすさ、現在の正の一意性／原則 4

### MP-23 状態遷移表の空いたマス ★★

**文脈**：業務の対象（注文など）は、状態を移り変わる。要求資料は、たいてい「できること」だけを書く。

**問題**：**状態の移り変わりを図や文で書くと、「できないこと」と「まだ決めていないこと」が見えず、取消と結果の行き違いのような組み合わせが抜ける。**

**フォース**
- 図は、全体の流れを伝えやすい。
- 状態と出来事のすべての組み合わせを並べると、表が大きくなる。
- ほかのコンテキストから届く事実は、取消などと前後が入れ替わりうる。

**解決**：したがって、状態の移り変わりを、状態と出来事のすべての組み合わせを並べた表で書き、空いたマスを、受け付けない、起こりえない、まだ決まっていない（未決事項を引く）のどれかで埋めよ。出来事には、届く事実も入れ、前後が入れ替わる組み合わせも行にする。終端の状態、そこからやり直せるか、放置されたときの扱いを書く。

**結果として生じる文脈**：抜けが、空いたマスとして見える。状態遷移図は、この表から描く。

**事例**
- 例題では、取り消した注文に、後から与信の承認や在庫の引当が届く行を、状態遷移表に置く。

**確かめた範囲**：AI による試用（例題、整理された要求から入る手順）で、状態と出来事のすべての組み合わせを埋め、取消と結果の行き違いを未決事項にした。

**関連する既知の手法**：状態遷移表 [ISTQB 2024]、終端の状態と放置されたものの終わらせ方 [Chassaing 2021]、すべての経路を安定した状態で終わらせる規則 [Brandolini 2022]

**主な価値基準と原則**：正直さ、業務事故の防止／原則 2

### MP-24 一語一義 ★

**文脈**：MP-03 で、ドメイン設計の言葉を用語集にまとめた。同じ語が、コンテキストによって違うものを指す（例：「お客様」が、受注では注文主を、与信では与信の対象の取引先を指す）。

**問題**：**一つの語に二つの意味を負わせると、読み手も AI も、一方の意味で他方を変えてしまい、不具合や誤った集計を生む。**

**フォース**
- 業務の人は、同じ語を使い続けたい。
- どちらかの意味に統一すると、もう一方の文脈の言葉が失われる。
- 識別子の接頭辞も、語と同じように意味を持つ。

**解決**：したがって、一つの語に一つの意味を当て、コンテキストごとに意味が違う語は、用語集にそれぞれの意味を書き、一方に別の名前を与えよ。接頭辞も一つの意味だけに使う。

**結果として生じる文脈**：言葉のずれが見つかったら、用語集を先に直す。読み手の語彙がモデリングの用語と違うときは、本文を読み手の言葉で書き、対応を用語集に置いてよい。

**事例**
- `[bobs-used-bookstore-sample@de81fc8 docs/glossary.md]` は、二つの意味を持っていた語を分けて定義している。

**確かめた範囲**：パターンを導いた題材で現れている。（人に関わる）

**関連する既知の手法**：コンテキストごとの言葉の違いを境界の手がかりにする [Brandolini 2009]

**主な価値基準と原則**：伝わりやすさ、現在の正の一意性／原則 4

### MP-25 決定者のいる品質シナリオ ★

**文脈**：MP-02 で、要件の層を定めた。品質（同時の処理、記録の保存、応答の速さなど）は、業務の危険から導かれる。

**問題**：**品質を最後に確かめるものとして扱うと、目標を誰が決め、いつ何で確かめるかが決まらないまま、確かめる作業が開発の終わりに偏る。**

**フォース**
- 数値の目標は、顧客もすぐには決められない。
- 推測した数値は、誰も決めていない決まりになる。
- 正しさの要求（同時に正しく保つ）と、度合い（同時に何件まで）は、決める人と置き場が違う。

**解決**：したがって、品質の要求を、品質シナリオとして要件の文書に置け。重要度、状況ときっかけ、期待する結果、度合いの目標、目標の決定者、確かめる担当と時期、証拠を書く。数値が決まっていなければ、推測せずに未決事項を引く。正しさの要求は業務ルールに置き、品質シナリオはその度合いだけを持つ。

**結果として生じる文脈**：アーキテクチャ設計の設計条件と品質評価は、品質シナリオを識別子で引く（MP-04）。

**事例**
- `[ddd-business-sample@70819ae example01-b2b-order-to-cash/docs/08_quality_drivers.md]` は、品質シナリオに重要度、目標の決定者、証拠を持たせている。

**確かめた範囲**：パターンを導いた題材で現れている。AI による試用（例題、整理された要求から入る手順）で、同時の注文を、業務ルール、品質シナリオ、未決事項に分けた。（人に関わる）

### MP-26 誤読を防ぐ判断の節 ★

**文脈**：文書を同じ型で埋めると、読みやすいが、項目の間の重みが見えなくなる。

**問題**：**直観に反する決まりが型の中に埋もれていると、読み手や AI が、誤りだと思って「直して」しまう。**

**フォース**
- 理由を書きすぎると、経緯の記録に近づく。
- 採らなかった案は、文書ではなく判断記録に置きたい（MP-07）。

**結果として生じる文脈**：文書を正しく読むのに、判断記録を読まずに済む。

**事例**
- `[bobs-used-bookstore-sample@de81fc8 docs/design/domain/aggregate-order.md]` は、集約の章の中に、固有の判断の理由を節として立てている。

**確かめた範囲**：パターンを導いた題材で現れている。（人に関わる）

### MP-36 業務の対象の形を、顧客と確かめる

**文脈**：MP-18 で、業務上の事実を背骨にした。事実と受け渡しの約束は、注文、明細、取引先のような業務の対象を、名前で運ぶ。画面、帳票、既存のテーブルには、その対象が何から成るかを示すような形が書かれている。

**問題**：**業務の対象が何から成り、何で見分けるかを、顧客と共有する文書に書く場所がないと、画面やテーブルやクラスの形が、確かめられないまま業務の形として通ってしまう。**

**フォース**
- 業務の対象が何から成るかは、顧客の知識である（例：注文には請求先が要り、見積には要らない）。
- 顧客は、データモデルの図や定義を、ほとんど深く読めない。値を入れた具体の一件なら、確かめられる。
- 対象を主役にした文書を作ると、事実の背骨（MP-18）が崩れ、データベースの表の定義書に近づく。
- 画面や帳票の形は、手がかりにはなるが、そのまま業務の形ではない。

**解決**：したがって、着手する機能に要る業務の対象のうち、初めて記録される業務上の事実か、外から受け取る約束があるものだけを、`domain/things.md` に書け。対象ごとに、対象の種類（出来事の記録か、続いて在るものか）、この対象が初めて記録される事実、この対象が持つ情報を変える事実や操作、同じ対象とみなす条件を書き、対象の形は表にする。状態を持つ対象は、状態ごとに列を立てた表にし、どの状態のときにどの情報があるかを書く。情報ごとに、その値がどこから来るかを書く。値を入れた見本を、顧客の資料から一件か数件置き、AI は値を作らない。読み合わせは値を入れた見本から始め、AI が見本と表から業務ルールの候補を問いにして出し、顧客が採ったものだけを表の行の決定にする。キー、データの型、継承、システムが付ける情報は書かない。選択肢のある部分は MP-28 で列挙し、図は表から描く（[notation.md](notation.md) §2.6、§3.3、§5）。

**結果として生じる文脈**：事実と受け渡しの約束は、業務の対象の名前を書くだけで、その対象が何から成るかを `things.md` から引ける。どの情報が、どの状態のときにあり、その値がどこから来るかが、文書から読める。画面とテーブルの形は手がかりとして読み、対象の形には写さない（AP-19）。

**事例**
- 例題「受注と与信」の `things.md` は、注文を、状態ごとに列を立てた表で書き、同じ注文とみなす条件と、値を入れた見本を、未決事項にしている。
- 例題「家電の修理受付」の `things.md` は、同じ用紙を使う見積と修理を、二つの対象に分けている。

**確かめた範囲**：AI による試用（家電の修理受付）で、同じ用紙を使う二つの業務を二つの対象に分け、画面の項目とテーブルの列を、そのまま対象の形にしなかった。顧客が表と値を入れた見本で確かめられるかは、人による試用で確かめていない。（人に関わる）

**関連する既知の手法**：ワークフローに関わるデータの形を、コンテキストごとに書いてドメインエキスパートと作業する [Wlaschin 2024 §2.4]。値と、変わっても同じものとして扱うものを、会話の言い回しで見分ける [Wlaschin 2024 §5.6、§5.7]。何が一つのものか、どういうときに同じかを問う [kawasima n.d.a]。属性ごとに、値の来し方と使い道を問う [Lauesen 2002 §2.3]。データを、現実的な値を入れた形で利用者と確かめる [Lauesen and Harning 2001]。標本のデータから制約の候補を出し、利用者が明示的に採ったものだけを加える [Ramdoyal 2010]。

**主な価値基準と原則**：判断の権限、伝わりやすさ、業務上の事実を軸にしたデータモデルへの写しやすさ／原則 4

### MP-27 ルールごとの三つの例 ★

**文脈**：業務ルールを、文章で正確に書こうとしている。

**問題**：**複雑なルールを文章で詳しく書くほど、文は長くなり、境界での振る舞いがかえって読み取れなくなる。**

**フォース**
- 例は、顧客にも書けて、読める。
- 例だけでは、網羅を保証できない。

**結果として生じる文脈**：例は、そのままテストの名前と中身になる（MP-14）。

**事例**
- `[ddd-business-sample@70819ae example01-b2b-order-to-cash/docs/10_business_spec_working_method.md]` は、ルールを三つの例に落とす手順を書いている。
- 例題では、使える与信の額が 150,000 円のとき、150,000 円ちょうどの注文を境界の例にする。

**確かめた範囲**：パターンを導いた題材で現れている。AI による試用（例題、整理された要求から入る手順）で、業務ルールと判定に例を置いた。（人に関わる）

**関連する既知の手法**：ルール・例・質問の組 [Wynne 2015]

### MP-28 取りうる形を列挙する ★

**文脈**：業務の対象や判定の答えは、状態や場合によって、持つ情報が違う。

**問題**：**データの形を文章や真偽の印で書くと、業務では起こりえない状態や結果の組み合わせを、文書の上で締め出せない。**

**フォース**
- 記法を厳密にするほど、顧客との会話から遠ざかる。
- 記法で書いた形が、表と食い違うことがある。
- コードができたら、構造の正本はコードになる。

**解決**：したがって、業務上の形（事実が運ぶ情報、判定の答えが運ぶ情報、状態ごとに持つ情報）を、「すべて必要」と「どれか一つ」の組み合わせで列挙せよ。顧客と共有する文書では、記法の部分集合を、例と表に並べて使い、読み合わせの場で確かめる。論理モデルでは、コードがまだないときに、記法の全体で操作の入出力を書き、拒否や失敗も結果の選択肢の一つにする。答えと状態の名前は表で定義した名前を使い、形の定義は一か所に置く。コードができたら、型の名前と属性の表に置き換える。

**結果として生じる文脈**：形の選択肢が、関数型の設計の結果の型と、状態ごとの型に写る。

**事例**
- `[ddd-business-sample@70819ae example01-b2b-order-to-cash/models/20_credit.md]` は、与信を引き当てる操作の結果を、成功と拒否の選択肢で書いている。

**確かめた範囲**：パターンを導いた題材で現れている（論理モデルの形）。記法の部分集合を顧客が読めるかは、人による試用で確かめていない仮説である。（人に関わる）

**関連する既知の手法**：ドメインを AND と OR で書く記法 [Wlaschin 2024 §2.4]、業務の概念を表すミニ言語 [kawasima 2021]、状態ごとに別の型にする [Wlaschin 2013]

**主な価値基準と原則**：関数型アーキテクチャへの写しやすさ、合意の見分け／原則 1

### MP-29 論理型の語彙 ★

**文脈**：MP-28 で、形を列挙した。論理モデルの属性を書く。実装の型（整数、文字列、小数）で書くことが多い。

**問題**：**実装の型で属性を書くと、文書が実装技術に縛られ、通貨を伴う、負にならない、差である、といった業務上の意味が読み取れない。**

**フォース**
- 実装の型は、開発者に分かりやすい。
- 同じ実装の型でも、業務上の意味が違うものがある。
- 時間には、起きた時点、有効な期間、記録した時点の違いがある。

**解決**：したがって、業務上の意味を表す少数の論理型を定め、属性をそれで書け。意味が違うものは、実装の型が同じでも、別の論理型にする。時間は、発生日時、有効期間、記録日時を分ける。

**結果として生じる文脈**：既存のコードから入るときは、記法の全体の代わりに、論理型の属性の表で書く（[notation.md](notation.md) §4）。

**事例**
- `[bobs-used-bookstore-sample@de81fc8 docs/design/README.md]` は、論理型の一覧を定め、属性を書いている。

**確かめた範囲**：パターンを導いた題材で現れている。AI による試用（題材と同じコードから入る手順）でも、論理型で属性を書いた。

**関連する既知の手法**：時間の軸を分ける考え（[data-modeling-pattern-language](https://github.com/matarillo/data-modeling-pattern-language)）

**主な価値基準と原則**：伝わりやすさ、業務上の事実を軸にしたデータモデルへの写しやすさ／原則 4

### MP-30 着手の直前に決める ★

### MP-32 会話の作成物を正本に転記する

**文脈**：ワークショップでは、付箋、絵文字の図、カードなど、会話のための表記を使う。

**問題**：**会話の作成物をそのまま残すと、参加しなかった人には読めず、どれが正かも決まらない。残さないと、合意したことが失われる。**

**フォース**
- 会話の表記は、その場では強力である。
- 写真や図は、テキストから再生成できない。
- 転記するのが AI だと、合意していないことが決定に紛れうる。

**解決**：したがって、会話の作成物は保存せず、終わったら、合意したことを文書の置き場に転記せよ。言葉は用語集、出来事は業務上の事実、業務で使う文書や帳票の情報は業務の対象の形、ルールと例と質問は業務ルールと未決事項、状態は状態遷移表、境界の候補はコンテキストの文書に移す。あるべき姿が何段階にもまたがり、決めた事項を反映する段階のブランチがまだないときは、反映待ちの決定事項に記録する（[document-system.md](document-system.md) §9）。決定者がその場で確かめた項目だけを決定にし、出所にワークショップの回を書く。

**結果として生じる文脈**：どの入口から入っても、同じ文書が残る（MP-03）。

**事例**：—

**確かめた範囲**：AI どうしのワークショップの模擬（例題。弱い証拠）で、会話から得たことを、文書の置き場に転記できた。人の話し手との場では、確かめていない。（人に関わる）

**関連する既知の手法**：作成物より学習が主だという立場 [Avanscoperta 2025c]、語り直して同意を得る [Hofer and Schwentner 2026a]、会話は記録より大事である [Cucumber 2026e]

**主な価値基準と原則**：判断の権限、現在の正の一意性／原則 1

### MP-33 挙動を固定してから直す ★

**文脈**：既存のコードから導いた文書の設計課題（MP-17）に沿って、コードを直す。

**問題**：**設計課題を手がかりにコードを直すと、それまでの振る舞いが変わったことが、誰にも気づかれないまま修正の中に紛れ込む。**

**フォース**
- 課題を見つけた勢いで、まとめて直したくなる。
- 挙動を変えることには、業務の判断が要る。
- 変えた挙動は、人に見えなければならない。

**解決**：したがって、直す前に、特性テストで現状の挙動を固定せよ。挙動を変えるときは、そのテストを意図して反転させ、差分として見せる。課題ごとに一つの変更にし、業務の判断が要るものは人に残す。

**結果として生じる文脈**：直した後に、文書を作り直す（MP-34）。

**事例**
- `[bobs-used-bookstore-sample@632e56a]` は、配達予定日の求め方を直す前に、いまの挙動をテストで固定したコミットである。

**確かめた範囲**：パターンを導いた題材で現れている。

**関連する既知の手法**：特性テスト [Feathers 2016]

**主な価値基準と原則**：保証の見分け、判断の権限／原則 1、原則 7

### MP-34 直した後に作り直す ★

**文脈**：MP-33 でコードを直した。文書は、直す前のコードから導いたものである。

**問題**：**直したコードに合わせて文書を差分で直すと、改訂の注記や旧版との対比がたまり、どれが現在の正かが読めなくなる。**

**フォース**
- 差分で直すほうが、手間は小さく見える。
- 作り直すと、識別子が振り直され、参照が切れうる。
- AI は、現在のコードから文書を作り直すのが速い。

**解決**：したがって、直し終えたら、文書を差分で直さず、現在のコードから作り直せ。作り直した後、旧版を参照する記述（コメント、作業の規律の中の参照）を消す。識別子は、振り直さずに済むよう、できるだけ引き継ぐ。

**結果として生じる文脈**：文書は、現在のコードの現在版になる（MP-06）。

**事例**
- `[bobs-used-bookstore-sample@de81fc8 docs/README.md]` は、直した後のコードから作り直した文書体系である。

**確かめた範囲**：パターンを導いた題材で現れている。

**主な価値基準と原則**：現在の正の一意性／原則 5

### MP-35 あるべき姿を変更案として書く

**文脈**：既存のシステムの現状（as-is）を書いた文書がある。ワークショップなどで、あるべき姿（to-be）をまとめて設計する。

**問題**：**現状を書いた文書にあるべき姿を書き足すと、現状とあるべき姿が混ざる。あるべき姿を別の文書にすると、本線に二つの正本ができる。**

**フォース**
- あるべき姿は、まとまった変更として設計したい。
- 顧客は、変更をまとめてレビューしたい。
- 現状の文書は、コードが変わるまで正しい。
- 顧客もチームも、移った先の全体の姿を一度に見たい。しかし、文書がコードと合っているかを確かめられるのは、コードを変えた段階ごとである。

**解決**：したがって、あるべき姿は、版管理のブランチで、文書を「あるべき姿が現在の正であるかのように」書き換え、時点を to-be にせよ。足した、または変えた不変条件の強制レベルは「未実装」とし、コードを変えたら測り直す。顧客には、ブランチの差分でレビューしてもらう。合意したら、同じブランチでコードを変え、強制レベルを測り直し、時点を as-is に戻してから取り込む。まだ決まらない点は、未決事項と設計課題に置く。あるべき姿が何段階にもまたがるときは、次の段階だけをブランチに書き、取り込んでから次の段階を見直す。その先の段階は、業務の決定が要るものを未決事項に、モデルと実装のずれを設計課題に置き、段階の順序は計画の道具に置く。前の段階で決めた事項は、該当する段階のブランチを作るときに、最初に反映する。

**結果として生じる文脈**：一つの文書に現状とあるべき姿が混ざらず、本線の正本は一つに保たれる。最終の姿も、本線の文書にならない。

**事例**：—

**確かめた範囲**：AI による試用（題材と同じコードから導いた文書に、あるべき姿を足す手順）で、ブランチの上に、あるべき姿の文書が差分として書かれた。顧客がブランチの差分でレビューする場面と、あるべき姿が何段階にもまたがる場合は、確かめていない。（人に関わる）

**関連する既知の手法**：現状の評価と将来の設計を反復して進める、Architecture for Flow Canvas [Kaiser 2025a]。現状から将来への進化を一歩ずつ描く、Team Topologies の図 [Team Topologies 2025b]。

**主な価値基準と原則**：現在の正の一意性、レビュー責任との一致／原則 6

## 5. 確かさの星

星は筆者の評価であり、確かめた範囲だけから決める。

| 星 | 意味 |
| --- | --- |
| ★★ | 公開された題材のうち、パターンを導くのに使っていないもので確かめた。人の読み手や話し手に関わるパターンは、人による試用で確かめたものに限る |
| ★ | 公開された題材で現れているが、それはパターンを導いた題材である |
| （なし） | 仮説。公開された題材でまだ現れていない |

- 各パターンには、星とは別に、次の二つの欄を置いた。
  - 確かめた範囲：どの題材で、AI と人のどちらが読み手の試用で確かめたか。
  - 関連する既知の手法：同じ解決を示す原典。原典があることは、星を上げる理由にしない。
- パターンを導いた題材での現れは、「事例」として書いた。確認とは数えない。
- 例題（[examples/order-credit](../examples/order-credit/)）は、パターンを導くのに使っていない題材である。AI による試用で確かめたことは、確かめた範囲にそう書いた。
- 人の読み手や話し手に関わるパターンには、確かめた範囲に「（人に関わる）」と書いた。これらは、人による試用で確かめるまで ★★ にしない。
