# 文書格納体系

この文書は、ドメインモデリングとドメインの文書化で、どの文書を、どこに、どの単位で置くかを定める。

- 対象：複雑な業務ルールを持つ IT システムの開発。AI に文書とコードを書かせ、人が判断する開発を前提にする。
- 読み手
  - 文書の置き場と書き方を決めるチーム
  - チームの中で文書を書き、読む AI
- 入口はどこでもよい。次の三つの入口のどこから入っても、同じ種類の文書が、同じ置き場に、同じ識別子とメタデータで残るように作ってある。
  - 整理された要求から入る
  - 既存のコードから入る
  - ドメインエキスパートとのワークショップから入る

手法ごとの手順は [processes.md](processes.md) に、記法は [notation.md](notation.md) に、用語は [glossary.md](glossary.md) にある。

## 1. 文書の二つの役割

文書には、二つの役割がある。どちらも重要である。

| 役割 | 文書に求めること |
| --- | --- |
| AI の入力 | 現在の正が一つに定まる。識別子で対象を指し、変更の影響範囲を機械的にたどれる。過去の記述というノイズがない |
| 人の理解の補助 | 認知の負荷を下げ、本質的な複雑さ（業務のルール、判定、境界）に集中させる。長く保守できる。読み手ごとの入口がある |

- この二つのどちらにも役立たない文書は、作らない。片方にしか役立たない文書は、ほかの文書と統合できないかを先に考える。
- コードとテストがはっきり表していること（実装の所在、型の細部、永続化）は、文書で言い換えない。言い換えた文書は、人には負荷になり、AI には食い違いの元になる。
- 上流の文書（顧客の要求資料、外部の API の仕様など）も、言い換えて第二の正本にしない。参照し、上流が決めていない点だけを書く。
- AI は網羅的な文書をたやすく作る。量を絞るのは、この体系の規則と、AI 向けの規律（`AGENTS.md`）の役目である。

## 2. 層と観点

### 2.1 層

層は、文書が答える問いで分ける。工程の順ではない。機能を縦に薄く作るときは、その機能に関わる層の文書だけを直す。

| 層 | 答える問い | 誰の言葉か | 決める人 | 顧客のレビュー |
| --- | --- | --- | --- | --- |
| 要求 | なぜ作るのか | 顧客 | 顧客（事業の責任者） | する |
| 要件 | 何を引き受けるのか | 顧客とチームが合意した言葉 | 顧客、プロダクトオーナー | する |
| 仕様（外部設計） | 外からどう見えるか | 顧客とチームが共有し、テストできる言葉 | 顧客とチーム | する |
| 内部設計 | 内部をどう作るか | チーム | チーム | しない |


### 2.2 観点

次の二つは、層を横断する観点である。層とは別の置き場を持つ。

| 観点 | 何か | 置き場 |
| --- | --- | --- |
| ドメイン設計 | 顧客と開発チームの共通理解。実装技術に依存しない。業務の言葉、境界と約束、業務上の事実、業務の対象の形、業務ルールと判定、業務の状態の移り変わりを表す | `domain/` |
| アーキテクチャ設計 | システムを何を条件に、どの方針と構成で作るか | `architecture/` |

- ドメイン設計は、顧客と共有するものだけを持つ。技術に依存しないが顧客と共有しないもの（集約、不変条件と強制レベル、操作の型、設計課題）は、論理モデルと呼び、内部設計の層に置く。
- 業務ルールと不変条件の線。顧客が決める、または合意しなければならないものは、業務ルールとしてドメイン設計に置く。たとえば「何と何を同時に正しく保たなければならないか」は業務ルールである。それをどの集約で、どこまで守るかは、論理モデルに置く。業務ルールに当たるかは、次の問いで判定する。
  - 業務の言葉で書けるか。
  - 決定者が、値や選択を決めるか。
  - 破れると、業務に損害が出るか。

## 3. 置き場

```text
docs/
├─ README.md            文書地図：置き場、層と観点、識別子の一覧、読み手ごとの入口
├─ questions.md         未決事項の台帳（入口を問わず一つ）
├─ decisions/           判断記録（DR）。最初の DR が要るときに作る
├─ product/             要求・要件
│   ├─ goals.md             目的、範囲、成功の観点、関わる人、優先する原則
│   ├─ quality.md           品質シナリオ
│   └─ upstream/            上流の写し（顧客の要求資料など。書き換えない）
├─ domain/              ドメイン設計（顧客と共有する）
│   ├─ glossary.md          用語
│   ├─ contexts.md          サブドメイン、境界づけられたコンテキスト、コンテキストマップ、受け渡しの約束
│   ├─ facts.md             業務上の事実と、事実の流れ
│   ├─ things.md            業務の対象と、その形（何から成り、何で見分けるか）
│   ├─ rules.md             業務ルール、判定と許される答え、例、ルールがない領域
│   └─ lifecycles.md        業務の状態の移り変わり（状態遷移表）
├─ spec/                仕様（外部設計）：ユースケース、画面、外部 API の振る舞い
├─ design/              内部設計
│   └─ model/               論理モデル
│       ├─ <コンテキスト>.md    集約、値、操作の型、ワークフロー、不変条件と強制レベル
│       ├─ shared.md            複数のコンテキストが共有する値
│       └─ issues.md            設計課題
└─ architecture/        アーキテクチャ設計
    └─ README.md            入口。七つの節の最小の中身。育ったビューや節は、このディレクトリに文書を足す
AGENTS.md               AI 向けの規律
```

- フォルダの名前が、層か観点を表す。文書のメタデータに、層を重ねて書かない。
- 要求・要件の正本がリポジトリの外（顧客の資料など）にあるときは、その写しを `product/upstream/` に置く。
  - 写しは書き換えない。`upstream/README.md` の表に、写しごとの取得元、版、取得日を書く。Word や Excel などの資料は、テキストに変換した写しも置く。
  - 上流が改訂したら、写しを丸ごと置き換える。写しの差分から、影響する項目をたどる。
  - 写しを置けない（機密、形式）ときは、`product/goals.md` に版と所在だけを書く。
  - `product/goals.md` には、要約と、写しの箇所への参照だけを置く。上流が決めていない点への決定のうち、業務ルールに当たるものは `domain/rules.md` に置く。
  - 要件と文書の項目の対応表は作らない。各項目の出所の欄が、その役を果たす。
- 業務で使っている帳票や画面（注文書の様式、いまのシステムの画面など）も、上流の写しとして置いてよい。置くのは、記入していない様式か、記入済みのものから個人の情報などを伏せた写しだけで、着手する機能が使うものに限る。写しは手がかりであり、その形をそのまま業務の対象の形にしない（[processes.md](processes.md) §1.6）。
- 小さな規模では、すべての文書を最初から作らなくてよい（§12）。

## 4. 文書の種類

### 4.1 文書ごとの役割

| 文書 | 答える問い | 読み手 | 決める人 | 更新のきっかけ | AI の用途 | 人の用途 |
| --- | --- | --- | --- | --- | --- | --- |
| `README.md` | どこに何があり、新しいものをどこに置くか | 全員 | チーム | 置き場や識別子の規則を変えたとき | 置き場と接頭辞を引く | 読み手ごとの入口 |
| `AGENTS.md` | AI は何をしてよく、何をしてはならないか | AI。人は承認のために読む | チーム | 規律を変えたとき | 作業の規律 | AI に課した規律を確かめる |
| `questions.md` | 何が決まっていないか。誰が、いつ決めるか | 顧客、チーム | 問いごとの決定者 | 空白や矛盾を見つけたとき。決まったとき | 推測で埋めてはならない所を知る | 決める予定を管理する |
| `decisions/` | なぜそう決め、何を採らなかったか | チーム、顧客 | 決定者 | 記録の線（§7.3）を超える判断が下されたとき | 採らなかった案を再び提案しない | 同じ議論を繰り返さない |
| `product/goals.md` | なぜ作り、何を引き受けるか | 顧客、チーム | 顧客、プロダクトオーナー | 事業の判断や、範囲の合意が変わったとき | 範囲の外の変更を避ける | 目的と範囲を共有する |
| `product/quality.md` | どの品質を、どの度合いで守り、何で確かめるか | 顧客、チーム | 目標の決定者 | 品質の目標や、確かめ方が決まったとき | 品質の制約を知る | 品質を誰がいつ決め、確かめるかを管理する |
| `domain/glossary.md` | どの言葉が何を指すか | 全員 | 顧客とチーム | 言葉のずれを見つけたとき | 名前の一致を確かめる | 共通の言葉 |
| `domain/contexts.md` | 業務をどこで分け、境界の間で何を約束するか | 顧客、チーム | 顧客とチーム | 境界や約束が変わったとき | 変更が及ぶ境界を知る | 責任の範囲を知る |
| `domain/facts.md` | どんな業務上の事実が起き、どうつながるか | 顧客、チーム | 顧客 | 新しい事実や流れが分かったとき | 事実の名前で、状態、約束、操作をつなぐ | 業務の流れを知る |
| `domain/things.md` | 業務の対象は何から成り、何で見分けるか | 顧客、チーム | 顧客 | 業務の対象が持つ情報や、同じ対象とみなす条件が分かったとき | 事実と受け渡しの約束が運ぶ業務の対象が、何から成るかを知る。名前の一致を確かめる | 何を記録し、何で見分けるかを確かめる |
| `domain/rules.md` | 顧客が決めるルールと判定は何か。境界でどう振る舞うか | 顧客、チーム | 顧客 | ルールの決定、例の追加 | テストの種、拒否の名前 | 合意の対象 |
| `domain/lifecycles.md` | どの状態で、どの操作や出来事が許されるか | 顧客、チーム | 顧客 | 状態や遷移を決めたとき | 遷移の網羅を確かめる | 空いたマスを見つける |
| `spec/` | 外から何ができ、どう見えるか | 顧客、チーム | 顧客とチーム | 外部の振る舞いを合意したとき | 実装の対象と、受け入れの条件 | 画面や API を合意する |
| `design/model/<コンテキスト>.md` | モデルは何を、どこまで守っているか | チーム、AI | チーム | モデルや実装を変えたとき | 影響範囲を特定する。存在しない保証を前提にしない | 実装を読まずに構造を知る |
| `design/model/shared.md` | 複数のコンテキストが共有する値は何か | チーム、AI | チーム | 共有する値を変えたとき | 共有する値を変えたときの影響範囲を知る | 共有の範囲を小さく保つ |
| `design/model/issues.md` | モデルはどこが歪んでいるか | チーム | チーム | 歪みを見つけたとき、直したとき | 直す対象を知る | 改善を計画する |
| `product/upstream/` | 上流は何を求めているか（写し） | 全員 | 上流（顧客など） | 上流が改訂したとき | 要求の原文を読み、項目の出所を確かめる | 改訂の差分を見る |
| `architecture/` | 何を条件に、どの方針と構成で作るか | チーム。顧客は設計条件とシステムコンテキストを読む | チーム（アーキテクト） | 設計条件や構成を変えたとき | 構成要素と境界の対応、横断的な方式に従う | 全体像を知る。ビューで構成を理解する |

### 4.2 文書ごとの中身

| 文書 | 含む | 含まない |
| --- | --- | --- |
| `questions.md` | 未決事項（`Q-`）。種別（業務、品質、範囲、アーキテクチャ）、問い、関係する識別子、決定者、決める時期。一つの未決事項には、一つの問いだけを書く。決める時期は、作業の節目（「与信の判定に着手する前」など）で書いてよい。決定者が分からないときは、決定者の欄を `？` にし、決める時期の欄に、決定者を誰がいつまでに確かめるかを書く。反映待ちの決定事項（決めたが、反映する段階のブランチがまだないもの。§9）は、別の節に、識別子、決めた事項、決定者と決定の日付（出所）、反映する段階を書く | 改善案の一覧（設計課題に置く）。決まった問い（決まったら、反映して消す） |
| `product/goals.md` | 目的、範囲と範囲外（既製の製品や外部のサービスで賄うコンテキストは、範囲の行に、賄う製品やサービスと一緒に書く。連携するだけの外部のシステムは、範囲外に書く）、成功を確かめる観点、関わる人（利用者には、その人がこのシステムでしたいこと）、優先する原則 | 推測した数値目標。業務ルールに当たる原則（`domain/rules.md` に置いて引く）。顧客やチームの望みを、利用者のニーズとして書くこと |
| `product/quality.md` | 品質シナリオ（`QS-`）。重要度、状況ときっかけ、期待する結果、度合いの目標、目標の決定者、確かめる担当と時期、証拠 | 推測した数値（決まっていなければ `Q-` を引く）。正しさの要求（§4.3） |
| `domain/glossary.md` | 誤解が実装やテストに響く言葉。コンテキストごとに意味が違う言葉。単独で使わない言葉。画面の見せ方の名前（一覧、カレンダー、受信箱など）のうち、その見せ方そのものについて、業務が決めること（業務ルール、状態）があるもの | すべての言葉の辞書。画面の表示の文言。状態や事実の意味（それぞれの文書を引く）。それ以外の、画面の見せ方の名前（一覧、カレンダー、受信箱、ダッシュボードなど） |
| `domain/contexts.md` | サブドメインと分類（中核、支援、汎用）。コンテキストの名前、責任、持つ情報、持たない責任。コンテキストどうしの関係の種類。受け渡しの約束（送り手、受け手、運ぶ情報、重複を見分ける鍵、失敗したときの扱い） | 通信の方式、同期か非同期か、プロセスやサーバーの分け方（アーキテクチャ設計に置く） |
| `domain/facts.md` | 業務上の事実の一覧（過去形の名前、どのコンテキストで起きるか、運ぶ情報、意味）。取消や訂正も、元の事実を引く新しい事実として書く。主な流れを、事実の並びとして書いたもの。運ぶ情報の書き方（業務の対象の名前で書く。その時点の値は名前で分ける）は、[notation.md](notation.md) §2.4 による。事実が運ぶ情報は、記法の部分集合のブロックで書く（選択肢ごとに運ぶ情報が違うとき） | 技術的なログ。イベントの配信方式。業務の対象が何から成るか（`things.md` に置く） |
| `domain/things.md` | 着手する機能に要る業務の対象のうち、初めて記録される事実か、外から受け取る約束があるもの。コンテキストごとに節を分け、対象ごとに次を書く。対象の種類（出来事の記録か、続いて在るものか）。この対象が初めて記録される事実と、この対象が持つ情報を変える事実や操作。同じ対象とみなす条件。この対象の形を書く表（状態を持つ対象は、状態ごとに列を立てる。情報ごとに、その値がどこから来るかを書く）。値を入れた見本（値は顧客の資料から取る）。選択肢のある部分は、記法の部分集合のブロックでも書く。外から受け取る対象は、このコンテキストが使う部分と、持ち主のコンテキストを書く。表から描いた、対象のつながりの図（[notation.md](notation.md) §5）。書き方は [notation.md](notation.md) §2.6 | 初めて記録される事実も、外から受け取る約束もない対象。キー、データの型、継承など、システムの組み立て方に関わること。記録した日時、更新した人、削除の印など、システムが付ける情報（どちらも論理モデルに置く）。業務ルールの文そのもの（要点は値まで書いてよい。識別子を添える）。資料にない値を使った見本 |
| `domain/rules.md` | 業務ルール（`RULE-`）と、その出所（要求資料の箇所、決めた人、ワークショップの回）。判定（`JDG-`）と、その問い、入力、許される答え、答えごとに生じる業務上の事実の名前。入力は、どの値をどの定義で使うか（例：税込みか税抜きか、残高に何を含めるか）まで書き、決まっていなければ未決事項を引く。入力ごとに、その値がどこから来るか（業務上の事実の名前、受け渡しの約束、業務ルールの識別子）も書く。顧客が決める計算（例：注文の金額の出し方）も、業務ルールとして書く。判定には、どの順で確かめるかという手順を書かない（入力への依存だけを書く）。許される答えが運ぶ情報は、記法の部分集合のブロックで書く（選択肢ごとに運ぶ情報が違うとき）。例は、業務ルールにはふつうの例、境界の例、違反の例を、判定には許される答えごとの例と境界の例を置く。業務ルールがない領域（ドメイン未定義のものだけ。未決のものは書かず、未決事項に置く）。直観に反するルールには、現在の理由を書く | モデルがルールをどう守るか（論理モデルに置く） |
| `domain/lifecycles.md` | 業務の対象ごとの状態遷移表（現在の状態、操作または出来事、条件、次の状態）。出来事は `facts.md` の事実の名前で書く。ほかのコンテキストから届く事実（例：判定の結果）も行にし、取消などとの前後が入れ替わる組み合わせも行にする。終端の状態と、そこからやり直せるか（再提出など）、放置されたときの扱い。どの状態でも許されない組み合わせ | 状態を表す型の細部。状態を事実から導くか、保持するか（論理モデルに置く）。状態ごとに持つ情報（`things.md` の、状態を持つ対象の形の表に置く） |
| `spec/` | ユースケース（`UC-`）、画面（`SCR-`）、外部 API の振る舞い。ユースケースは、業務ルール、判定、操作を識別子で引く。画面だけが持ち、業務ルールとして合意していない決まりは、ユースケースの中に「画面だけの決まり」として隔離し、未決事項を引く。合意したら `domain/rules.md` に移す。画面に出す項目のうち、値がどこから来るのかが見つからないもの（画面だけの項目）も、同じように隔離し、未決事項を引く。入力しても記録しない項目（検索の語、並べ替えの指定など）は、画面だけの項目として書くだけでよい。読み取りモデル（照会や統計が返す応答の形）。画面のワイヤーフレーム（画像）は、例外として置いてよい。項目と操作の正本はユースケースで、ワイヤーフレームは配置だけを持つ | 業務ルールの本文。ユースケースの中の業務上の条件分岐と計算式 |
| `design/model/<コンテキスト>.md` | 集約（`AGG-`）、値（`VO-`）、操作（`OP-`）の入出力、ワークフロー（操作の並び）、不変条件（`INV-`）と強制レベル、強制でない不変条件の是正の扱い、差し替えられる判断（`POL-`）。強制レベルごとの件数。業務の状態ごとに、業務上の事実から導くのか、それ自体を保持するのか。直観に反する設計には、現在の理由を書く。コードがまだないときは、記法の全体で書いてよい | 業務ルールの本文（識別子で引く）。業務上の形の定義（`domain/` の名前を引く）。実装の型名、永続化の詳細 |
| `design/model/shared.md` | 複数のコンテキストが共有する値。共有するコンテキストの名前 | 共有の関係の種類（`domain/contexts.md` に置く） |
| `design/model/issues.md` | 設計課題（`ISSUE-`）。重大度、関係する識別子、現象、影響、改善の方向 | 現状の記述（論理モデルの本文に置く） |



### 4.3 置き分けの約束

同じ事実が二つの文書に書かれやすい組み合わせについて、どちらを正本にするかを決めておく。

| 事実 | 正本 | ほかの文書での扱い |
| --- | --- | --- |
| 判定の許される答えと、それぞれから生じる業務上の事実 | `domain/rules.md` の判定の表 | 状態遷移表と受け渡しの約束は事実の名前を、操作の結果は答えの名前を引く |
| 業務上の形（業務の対象の形と、状態ごとに持つ情報、事実が運ぶ情報、判定の答えが運ぶ情報） | `domain/` の `things.md`（業務の対象。状態による違いも含む）、`facts.md`、`rules.md`。状態の名前は `lifecycles.md` | 事実の表と受け渡しの約束は、対象の名前で引く。論理モデルは名前で引き、モデルに要る構造（キー、集約の境界など）だけを足す |
| 状態の名前と意味、許される遷移 | `domain/lifecycles.md` | 用語集は名前だけを載せて引く。論理モデルは、遷移の順序を守る不変条件を、強制レベル付きで書き、状態遷移表を引く |
| 業務ルールの文 | `domain/rules.md` | 不変条件は、守るルールの識別子を引き、文を写さない。業務の対象の形の表は、要点を値まで書いてよく、そのときは識別子を添える（食い違うときは `rules.md` が正） |
| 正しさの要求（同時に正しく保つこと、何を記録に残すか） | `domain/rules.md` | 品質シナリオは、その度合いと数値（同時に何件まで、何年残すか）だけを持ち、ルールを引く |
| 具体例 | `domain/rules.md`。業務ルールの例にない、業務の対象の形の例だけは `domain/things.md` | 事実の流れ、品質シナリオ、ユースケース、業務の対象の形の表は、例を持つルールの識別子で引く |
| 業務の流れ（事実の並び） | `domain/facts.md` | 論理モデルのワークフローと、ユースケースの手順は、事実の名前を引く |
| 操作の入出力 | 論理モデル（`OP-`） | ユースケースは操作の識別子を引く |
| 一つのトランザクションで確定する範囲 | アーキテクチャ設計の、境界どうしの対応の表（§10.2） | 論理モデルの集約の境界と、不変条件の強制レベルは、この表を前提にする |
| 優先する原則のうち、業務ルールに当たるもの（例：確定した過去は書き換えない） | `domain/rules.md` | `product/goals.md` は識別子で引く |
| 不変条件の一覧 | 論理モデルの各コンテキストの文書 | 総覧を作らない。強制レベルごとの件数だけを各文書に書く |
| 決定者 | 決めた項目（業務ルール、判定などの出所の欄） | DR は項目の識別子を引く |
| 既製の製品（パッケージ）や外部のサービスが定める API とデータの形 | 相手の文書（上流の文書の一つ。§1）。`product/upstream/` に写しを置かず、`architecture/README.md` のシステムコンテキストの節に、版と所在を書く。要求資料の一部として受け取ったときは、§3 の上流の写しとして扱う | `domain/contexts.md` の受け渡しの約束には、相手の文書が決めていない点（運ぶ情報の業務上の意味、重複を見分ける鍵、失敗したときの扱い）だけを書く。外部との連携の完了条件は、失敗したときの扱いに含める |
| 既製の製品の設定で実現する業務ルール | `domain/rules.md`（コードで実現する業務ルールと同じ所） | 設定の手順は書かない |

### 4.4 図と派生ビュー

人の理解を助ける図や、複数の正本をまとめたビュー（例：コンテキストと構成要素とチームの対応の概観）の扱い。ドメイン設計にも、アーキテクチャ設計にも当てはめる。

- 既定では、図は Mermaid などのテキストの定義で文書に埋め込み、表示のときに描く。テキストの定義そのものが正本である。
- 派生物（正本から作った図や文書）は、次の三つを満たすときだけ、git に置いてよい。
  1. 正本から道具で生成する。
  2. 生成し直して差分がないことを、道具で確かめられる。
  3. 先頭に、派生物であることと、生成元を書く。
- AI は、派生物を直接直さない。派生物を正本として引かない。
- 表から描く図（状態遷移図、コンテキストマップの図、業務の対象の図）は、表が正本である。道具で生成しなくても、次の二つを守れば、表のすぐ後に置いてよい。置くかどうかの基準は、[notation.md](notation.md) §5 による。
  1. 図の直前に、元の表を一行で書く。図の要素ごとに、リンクや識別子を付けなくてよい。
  2. 表を直したら、同じ変更の中で図も描き直す。図だけを直さない。
- それ以外の、手で描いた図と、ずれを検出できない「参考」の文書は、置かない。説明のための図は、合意の場で作って捨てる。
- AI の出力は、生成し直しても同じにならない。そのため、AI に作らせたまとめは、多くの場合この条件を満たさない（§14）。

## 5. 識別子

- 一つの事実は、一か所でだけ定義する。ほかの文書からは、識別子で引く。本文を写さない。
- 接頭辞は、体系の中で一つの意味だけを持つ。一覧は `README.md` に置く。
- 識別子は、変更の依頼、課題の報告、AI への指示でも使う。
- 識別子の番号は、項目を消しても再び使わない。


| 接頭辞 | 意味 | 定義する文書 |
| --- | --- | --- |
| `Q-` | 未決事項 | `questions.md` |
| `DR-` | 判断記録。アーキテクチャに関するもの（ADR）も同じ接頭辞を使い、種別で区別する | `decisions/` |
| `QS-` | 品質シナリオ | `product/quality.md` |
| `RULE-` | 業務ルール | `domain/rules.md` |
| `JDG-` | 判定 | `domain/rules.md` |
| `UC-` | ユースケース | `spec/` |
| `SCR-` | 画面 | `spec/` |
| `AGG-` | 集約 | `design/model/` |
| `VO-` | 値 | `design/model/` |
| `OP-` | 操作 | `design/model/` |
| `INV-` | 不変条件 | `design/model/` |
| `POL-` | 差し替えられる判断 | `design/model/` |
| `ISSUE-` | 設計課題 | `design/model/issues.md` |

- 境界づけられたコンテキスト、業務上の事実、業務の対象、業務の状態は、名前そのものを識別子として使う。名前を定義する文書は、それぞれ `contexts.md`、`facts.md`、`things.md`、`lifecycles.md` である。名前を変えるときは、同じ変更の中で、名前を引くすべての箇所を直す。
- 例は、それを持つルールの識別子に番号を付けて引く（例：`RULE-CREDIT-02` の例 2）。
- 識別子の中に、コンテキストや集約の略称を入れてよい（例：`RULE-CREDIT-02`、`INV-ORDER-03`）。略称は、境界を見直しても変えずに済む業務の領域の名前にする。識別子を振り直すと、参照が切れるからである。

## 6. メタデータと印

### 6.1 文書のメタデータ

製品を記述する文書（`README.md`、`AGENTS.md` のような規約の文書を除く）は、先頭に次を書く。

```yaml
---
source: requirements   # requirements（要求資料）／code（コード）／workshop（ワークショップ）／team（チームが書いた）
source-ref: <導出元の版や文書の識別子>
timepoint: to-be       # as-is（現状）／to-be（あるべき姿）
---
```

- `architecture/README.md` も、製品を記述する文書として、このメタデータを書く。
- `source` は、文書が主に何から書かれたかである。合意したかどうかは、文書の単位では書かない（§6.2 の項目の印で示す）。
- `timepoint` の `as-is` は、いま動いている業務やシステムの記述である。`to-be` は、これから作る、または変える姿の記述である。
  - 既存のシステムがなく、要求やワークショップから新しく作るときの文書は、`to-be` を本線に置く。
  - 既存のシステムの現状（`as-is`）を書いた文書を変えるときの扱いは、§9 による。
- 凍結した版を、フォルダ名で残さない。過去の版は、版管理のタグやコミットで指す。

### 6.2 項目の印

| 対象 | 印 | 値 |
| --- | --- | --- |
| `domain/` と `product/` の表のすべての行（用語、コンテキスト、受け渡しの約束、事実、業務の対象の形、業務ルール、判定、状態遷移の行、記法の部分集合のブロック、目的と範囲の項目、品質シナリオ） | 合意状態 | 仮説：AI か開発者が書き、まだ誰にも確かめていない。要確認：確かめる先と問いが決まっている（`Q-` を引く）。決定：決定者が確かめた（出所に、決定者と日付を書く。未決事項への回答やワークショップの回で決めたなら、それも書く） |
| 不変条件 | 強制レベル | 強制（モデルの振る舞いでは破れない）、表明（意図されているが、破る操作がある）、外部（モデルの外で守られる前提）、不成立（守られるべきだが、破られる）、未実装（守るコードがまだない。コードを作ったら測り直す） |
| 不変条件、業務ルール | 検証 | 自動テストで固定されているか（あり／なし） |

- 確かさの軸を、一つの印に混ぜない。合意（誰が決めたか）、保証（モデルが守っているか）、検証（テストで固定されているか）、導出元、時点は、別の軸である。合意済みで、かつ不成立、ということもありうる。
- 強制レベルが表明、外部、不成立の不変条件は、すべて設計課題に対応する項目を持つ。未実装の不変条件は、まだ作っていないだけで不具合ではないので、設計課題にしない。顧客が決めた業務ルールを守る不変条件が「不成立」なら、顧客が知るべきことなので、未決事項も立てる。
- 検証の向き。文書には「あり／なし」だけを書く。どのテストが固定しているかは、テストの名前に業務ルールや不変条件の識別子を入れ、道具で一覧にする。これは、コードから文書の識別子を引かない、という規則の例外になる。

### 6.3 AI と人の区別

- 決定の印を付けるのは、人の判断が記録に残っているときだけである。AI が決定の印を書くのは、記録に残った人の判断（決定者と日付、`Q-` への回答、ワークショップの記録）を写すときに限り、その出所を項目に書く。
- AI は、モデルの案を仮説として書いてよい。たとえば、境界づけられたコンテキストの分け方、業務上の事実や状態の名前、判定の候補、決める時期の目安である。資料に案の根拠がなくても、仮説の印を付けて書き、確かめる未決事項を立てる。
- AI が推測で補ってはならないのは、業務の値と基準と選択である。たとえば、しきい値、期限、判定の基準、二つの記述が食い違うときにどちらを採るか、である。これらは未決事項にする。食い違う記述は、表のマスや項目でも、どちらも採らない。値の欄は `？` にして未決事項を引き、食い違う記述を、それぞれの出所とともに並べる。
- 読み合わせやワークショップで、決定者が要約の読み上げに同意したときは、その要約が識別子か中身ではっきり指した項目だけを決定にする。要約が指さなかった項目は、仮説のままにする。
- 業務の対象の形の表と、記法の部分集合のブロックに決定の印を付けるのは、読み合わせの場で、顧客が問い（[notation.md](notation.md) §3.3）に答えた後に限る。見た目でよいと言われただけでは付けない。

## 7. 判断記録（DR）

### 7.1 スナップショットと判断記録

- `docs/` の文書は、どれも最新のスナップショットである。現在の正だけを書く。変更の前後、移行中の記述、変更履歴の節、取り消し線を残さない。
- 判断・意思決定の記録は、判断記録（DR）として、スナップショットとは別に置く。アーキテクチャに関する判断記録が ADR である。すべての判断記録を ADR と呼ばない。
- 決めた内容の正本は、それを反映したスナップショットにある。スナップショットを正しく読むために、DR を読まなければならない状態にしない。

### 7.2 最小の形式

```markdown
# DR-0007 与信の判定は税込みの金額で行う

| 項目 | 内容 |
| --- | --- |
| 種別 | 業務（ADR のときは「アーキテクチャ」） |
| 有効性 | 有効（置き換えられたら「置き換え済み → DR-00xx」） |
| 問いの要旨 | 判定の入力の金額を、税込みと税抜きのどちらにするか（Q-02） |
| 反映した項目 | JDG-CREDIT-01 |

## 理由

## 採らなかった案と、その理由
```

- 決めた人と日付は、反映した項目の出所に書く（§4.3）。DR には書かない。
- 問いは、要旨を 1 行で書く。未決事項は決まったら台帳から消すので、`Q-` の番号だけでは読めなくなる。
- 具体例は DR に書かない。業務ルールの例として `domain/rules.md` に置く。

### 7.3 記録の線

次の両方に当たる判断だけを、DR にする。それ以外の判断の理由は、コミットのメッセージに書く。

1. 未決事項を解いた判断で、採らなかった選択肢が、資料か会話の中に実際にある。
2. 決定者が、記録を求めた。決定者は、元に戻す費用や誤ったときの事故が大きい領域では、記録を求めることを既定にする。そうした領域の例は、金銭、監査、権限、個人情報、データの消失、外部との連携の完了条件である（例であり、これに限らない）。

- 決定者とは、その事柄を決める権限を持つ人である。業務は顧客、範囲はプロダクトオーナー、アーキテクチャはチームのアーキテクトが決める。
- 記録を求めるかは決定者が決め、未決事項を閉じるとき（またはその変更の PR）に残す。AI は、記録を求めるかを決定者に尋ねてよいが、自分で決めない。
- AI や開発者の局所的な選択は、DR にしない。

### 7.4 判断の節と DR の分担

| 置き場 | 書くこと |
| --- | --- |
| スナップショットの中の判断の節（`rules.md` のルール、論理モデルの集約など） | 文書を正しく読むのに要る、現在の理由。直観に反する決まりが、なぜそうなっているか |
| DR | 採らなかった案と、その理由 |

### 7.5 誰が DR を書くか

判断するのは人である。AI は、人が下した判断を DR に書き起こしてよい。AI は、自分の判断を DR として残さない。

### 7.6 アーキテクチャ設計から引く ADR

アーキテクチャ設計は、現在有効な ADR のうち、重要なものだけを引く。ADR の全件の索引にしない。

## 8. 二つの台帳

| 台帳 | 何か | 決める人 |
| --- | --- | --- |
| 未決事項（`questions.md`） | 決める権限を持つ人の判断を待つ問い。空白と矛盾を、推測で埋めずにここへ置く | 問いごとの決定者 |
| 設計課題（`design/model/issues.md`） | 現状のモデルや実装が、あるべき姿とずれている点 | チーム |

- 未決事項が決まったら、次の順に進める。
  1. スナップショットの項目を直し、合意状態を決定にし、出所に決定者と日付を書く。
  2. 記録の線を超えるものだけ、DR を残す。
  3. 未決事項を台帳から消す。消した経緯は、コミットのメッセージに残す。
- 決めた事項を反映する段階のブランチが、まだないとき（あるべき姿が何段階にもまたがるとき。§9）は、1〜3 の代わりに、未決事項を「反映待ちの決定事項」の節に移す。該当する段階のブランチを作るときに、1〜3 を行う。
- 「取り決めがない」ことも、事実として書く。ルールがない領域は `domain/rules.md` に、モデルが規定していない事項は論理モデルに、「ドメイン未定義」と書く。
- 「ドメイン未定義」と「未決」は違う。
  - ドメイン未定義は、決まりがないことが事実である状態である。既存のコードに規定がない場合と、決定者が「ここには決まりを置かない」と決めた場合がこれに当たる。
  - 未決は、まだ誰も決めておらず、決める人がいる状態である。顧客が「まだ決めていない」と述べた事項も、未決である。
  - ドメイン未定義の事項を決めるべきだと分かったら、未決事項を立てる。

## 9. 現状とあるべき姿

- 一つの文書の中で、現状（as-is）とあるべき姿（to-be）を混ぜない。
- あるべき姿のうち、まだ決まっていないものは、未決事項か設計課題に置く。
- 既存のシステムの現状を書いた文書があり、あるべき姿をまとめて設計するとき（例：既存のコードから現状を導いたあと、ワークショップであるべき姿を詰めるとき）は、版管理のブランチで、文書を「あるべき姿が現在の正であるかのように」書き換え、`timepoint: to-be` にする。顧客には、そのブランチの差分（PR など）でレビューしてもらう。合意したら、同じブランチでコードを変え、`as-is` に戻してから取り込む。
- コードを変える前のブランチでは、あるべき姿で足した、または変えた不変条件の強制レベルを「未実装」と書く。コードを変えたら、測り直す。ブランチを取り込むときに、「未実装」が残っていないことを確かめる。
- 新しいシステムで、実装の前に論理モデルを書くときも、不変条件の強制レベルは「未実装」と書く。
- あるべき姿が何段階にもまたがるときは、次の段階だけをブランチで書く。その段階を取り込んだら、次の段階を見直す。
  - その先の段階のうち、業務の決定が要るものは未決事項（決定者は顧客）に、モデルと実装のずれは設計課題に置く。設計課題はチームの文書なので、業務の側の将来の姿を置かない。
  - その先の段階について前の段階で決めた事項は、`questions.md` の「反映待ちの決定事項」の節に記録し、該当する段階のブランチを作るときに、最初に文書へ反映する（§8）。文書体系の外の記録に残す変種と、その条件は、[pattern-language.md](pattern-language.md) §2.2 にある。
  - 段階の順序と見通しは、あるべき姿の記述ではなく、計画である。文書の正本にせず、計画の道具（課題の記録など）に置く。最終の姿を、本線の別の文書として置かない。

## 10. アーキテクチャ設計

### 10.1 最小の中身

アーキテクチャ設計は、専用のディレクトリ `architecture/` に置く。入口の `architecture/README.md` に、次の七つの節の最小の中身を書くことから始める。書くことのない節には、ないことを 1 行で書く。ビューや節が育って一つの文書で表しきれなくなったら、同じディレクトリに文書を足し、入口から引く。図は §4.4 に従う。

- 規模が大きく、ビューが多いときは、構成要素と関係のモデルをテキストで一つ置き、図と概観をそこから生成してもよい（§4.4 の派生物の条件に従う）。

| 節 | 答える問い | 書くこと | ほかの文書との接点 |
| --- | --- | --- | --- |
| 概要・設計条件 | 何を条件に設計するか | 対象範囲、品質目標、前提と制約 | 品質目標は `QS-` を引く |
| 基本方針 | どの原則と判断で作るか | 設計原則、技術の選定、重要な判断 | 重要な判断は、有効な ADR を引く。汎用の設計原則は外部の指針を引き、写さない |
| システムコンテキスト | システムの外に何があり、何をやり取りするか | システムの境界、外部のシステムと連携 | コンテキストマップ（`domain/contexts.md`）とは別物 |
| 論理アーキテクチャ | どの構成要素が何を受け持ち、どのデータを所有するか | 構成要素、責務と依存、データの所有 | 構成要素と境界づけられたコンテキストの対応（§10.2） |
| 実行時・配置 | どう動き、どこに置くか | 処理の流れ、実行環境、配置と冗長化。トランザクションの範囲、同期と非同期の選択 | 業務上の事実の流れ（`domain/facts.md`）を引く |
| 横断的な方式 | 全体で揃える方式は何か | セキュリティ、データと通信、エラー処理、監視と運用、可用性と性能 | エラー処理では、業務上の拒否（`domain/rules.md` の判定と許される答え）と、技術的な失敗を分ける |
| 品質評価・リスク | 品質目標をどう満たし、どう確かめ、何が危ないか | 品質要求との対応、品質の確かめ方、技術的なリスク | `QS-` を引く |

### 10.2 境界どうしの対応

境界づけられたコンテキスト、集約、構成要素（モジュール）、トランザクション、配置の単位、チームは、別の概念である。その対応はアーキテクチャ設計で決めて、次の表に書く。

| コンテキスト | 構成要素 | 一つのトランザクションで確定する範囲 | 配置の単位 | 受け持つチーム |
| --- | --- | --- | --- | --- |

- 受け持つチームの欄には、コンテキストごとに一つのチームを書く。一つのチームは、複数のコンテキストを受け持ってよい。顧客やほかのチームが、コンテキストの言葉と約束を確かめる相手を、一つにするためである。既製の製品や外部のサービスで賄うコンテキストには、相手との窓口になるチームを書く。
- ドメイン設計は、特定の対応を前提にしない。たとえば、コンテキストの間を非同期のイベントで結ぶことを、ドメイン設計で決め打ちしない。
- 業務が、境界をまたぐ結果について、そろうまでの時間を気にする場合（例：「承認した直後に、在庫の確保の結果まで見えなければならない」）は、それを業務ルールとして `domain/rules.md` に書く。方式とトランザクションの範囲は、この表で決める。
- 一つのアプリケーションと一つのデータベースで作るなら、複数のコンテキストの事実を一つのトランザクションで確定してよい。その場合も、コンテキストの間の受け渡しの約束は `domain/contexts.md` に書き、ほかのコンテキストのデータを直接書き換えない。

## 11. 入口ごとの書き始め

| 入口 | 正本 | 最初に書く文書 | 最初の印 |
| --- | --- | --- | --- |
| 整理された要求から | 顧客の要求資料（`product/upstream/` の写し） | `questions.md`（空白と矛盾）、`domain/glossary.md`、`domain/rules.md`、`domain/facts.md`、`domain/things.md`、`domain/lifecycles.md`、`domain/contexts.md` | `source: requirements`、`timepoint: to-be`。項目は仮説か要確認。要求資料に明記された事項も、顧客に確かめるまでは仮説とし、出所に写しの箇所を書く |
| 既存のコードから | 既存のコードとテスト | `design/model/`（強制レベルと検証）、`design/model/issues.md`、`questions.md`、それから `domain/` | `source: code`、`timepoint: as-is`。項目は仮説 |
| ワークショップから | ワークショップでの合意 | `domain/` の各文書と `questions.md`。会話のための作成物（付箋の壁、図）は保存しない | `source: workshop`。決定者がその場で確かめた項目だけが決定（出所にワークショップの回を書く）。ほかは仮説。論点は未決事項 |

- 組み合わせの例
  - 既存のコードから現状を導き、ワークショップであるべき姿を詰める（§9）。
  - 要求から立てた未決事項を、ワークショップで解く。
- どの入口でも、`domain/` の同じ文書に書く。入口の違いは、何から書き始めるかと、最初の印にだけ現れる。

## 12. 規模による縮め方

| 構成 | 文書 |
| --- | --- |
| 最小（要求かワークショップから入るとき） | `README.md`、`AGENTS.md`、`questions.md`、`product/goals.md`、`domain/` の 6 本、`architecture/README.md`。要求から入るときは `product/upstream/` の写し |
| 最小（既存のコードから入るとき） | 上に加えて、`design/model/` と `design/model/issues.md` |
| 必要になったら足すもの | `decisions/`（記録の線を超える最初の判断が出たとき。規模によらない）、`product/quality.md`（要求に品質の要求があれば、最初から作る）、`spec/`、`design/model/`（自分たちで作るコンテキストのうち、構造が複雑なもの）、コンテキストごとの文書の分割 |

- `product/goals.md` の範囲で、既製の製品や外部のサービスで賄うと決めたコンテキストには、`design/model/<コンテキスト>.md` を作らない。中の構造は相手が持つ。相手の文書の扱いと、受け渡しの約束に書く点は、§4.3 にある。
- コンテキストが一つしかなく、業務ルールも少ないときは、`domain/` の 6 本を、`glossary.md` と `domain.md` の 2 本にしてよい。`domain.md` は、`contexts.md`、`facts.md`、`things.md`、`rules.md`、`lifecycles.md` の中身を、同じ名前の節に分けて持つ。あとで分けるときは、節をそのまま同じ名前のファイルにする。

## 13. `AGENTS.md` に書く規律

- 文書には現在の正だけを書く。経緯、変更の前後、移行中の記述を書かない。変更の理由は、コミットのメッセージに書く。
- 一つの事実は一か所に書き、ほかからは識別子で引く。
- モデルの案（境界の分け方、事実や状態の名前、判定の候補）は、仮説の印を付けて書いてよい。
- 要求やコードにない業務の値、基準、選択を、推測で補わない。未決事項にする。
- 暫定の決まりを、自分で置かない。暫定にするかと、その中身は、人が決める（[pattern-language.md](pattern-language.md) §2.1）。
- 決定の印は、記録に残った人の判断を写すときにだけ書き、出所を添える。要約の読み上げへの同意で決定にするのは、要約がはっきり指した項目だけである。
- 人が下した判断は、DR に書き起こしてよい。自分の判断を DR にしない。記録を求めるかは、決定者に尋ねる。
- 現状の記述の中に、改善の方向を書かない。設計課題に書く。
- あるべき姿の段階のブランチを作るときは、最初に、反映待ちの決定事項（`questions.md`、または、ここに置き場を書いた文書体系の外の記録）を反映する。
- 記法の全体は、`design/model/` で、コードがまだないときにだけ使う。コードができたら、型の名前と属性の表に置き換える。
- 上流の文書やコードを言い換えて、第二の正本を作らない。上流の写しは書き換えない。
- 派生物を直接直さない。派生物を正本として引かない。表から描いた図は、表を直してから、同じ変更で描き直す。
- 業務の対象の形の表の、業務ルールと未決事項の欄に、業務ルールの値を書くときは、識別子を添える。食い違ったら、`rules.md` に合わせて直す。
- 記法の部分集合のブロックは、必ず例と表に並べる。業務の対象の形の表と、ブロックに決定の印を付けるのは、読み合わせの場で、顧客が問い（[notation.md](notation.md) §3.3）に答えた後に限る。
- 画面、帳票、試作の項目や配置を、そのまま業務の対象の形にしない。項目ごとに、値がどこから来て、何に使われるかを確かめてから、業務の対象の形の表、事実、受け渡しの約束、業務ルール、論理モデル、画面だけの項目に振り分ける（[processes.md](processes.md) §1.6）。
- 業務の対象の形の表に、キー、データの型、継承、システムが付ける情報を書かない。業務の対象の、値を入れた見本に、資料にない値を作らない。
- 事実や業務の対象が運ぶ値が、元の値が変わったら一緒に変わるのか、その時点の値のまま残るのかを、推測で決めない。
- 食い違う記述は、どちらも採らない。値の欄は `？` にして未決事項を引き、食い違う記述を出所とともに並べる。

## 14. AI が生成し、人がレビューするもの

AI が生成し、人がレビューするもの（例：上流の写しと文書の項目の対応を確かめた結果、上流の矛盾や不備を検出した結果）について、方向性だけを定める。具体的な形は、プロジェクトで実施するときに決める。

- これらは、ドメインや製品の現在の正を書いたスナップショットではなく、人がレビューするための作業の産物である。`docs/` の常設の文書にしない。
- 置き場は、レビューの場に付ける（PR の本文、課題の記録、CI の出力など）。
- 人がレビューして採った指摘だけを、体系の台帳に移す。矛盾や空白は `questions.md`、モデルの歪みは設計課題に移す。採った項目の出所には AI の点検であることを書き、合意状態は仮説か要確認から始める。
- 同じ点検を繰り返し使うなら、点検の手順（AI への指示や道具）を、文書ではなく道具として管理する。結果を git に置くなら、§4.4 の派生物の条件に従う。
